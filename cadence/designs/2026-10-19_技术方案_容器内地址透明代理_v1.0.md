## 0. 结论摘要

> **决策状态（2026-10-19 用户拍板）**：Q1 = **允许改 WSL VM 侧 relay**，走主方案 E-DNAT；Q3 = `relay.json` 已含全部真实地址；Q5 = 配置里**存在域名**，非全 IP（域名专章见 §7.4）。Q2（给容器加 `NET_ADMIN` 并重建镜像）按默认**不做**，A 方案仅作退路记录。另有两条硬约束：**R-S1 单入口单配置**（只跑 `relay.ps1`、只配 `relay.json`，域名同一次交互录入）与 **R-S2 规则固化**（除用户改配置外，规则不因重启消失或改变），见 §5.6、§6.2 步骤 3、§9.1。

1. **主方案：VM 侧 DNAT（方案 E-DNAT）**——在 WSL 的 podman machine 里用一条 **nft DNAT**（自建 `table ip cadence_dnat`，base chain `prerouting`，`priority dstnat - 1`），把 `<真实地址>:<端口>` 无状态改写成 `<socat 的实际 bindaddr>:<vmPort>`（通常等于网桥网关）。容器零特权、零镜像改动、零工程配置改动、容器重建后仍生效；复用已有 relay 子系统（root 通道、systemd 自恢复、事务式回滚均已存在）。**真机已验证通过（§11.3-E3，容器内 `CONNECT-OK`）**。
2. **域名场景的最终形态**：容器内解析链固定为「容器 `/etc/resolv.conf`（只指向网关）→ 网关 `:53` 的 aardvark-dns → 上游（VM `resolv.conf` → Windows/aTrust DNS）」。**只要解析结果是真实 IP，DNAT 自动接管，零额外配置**；解析失败、解析到错 IP（split-horizon）、或存在 AAAA 优先时，由 relay 子系统在 **VM 的 `/etc/hosts`** 里用标记段把 `域名 → 真实IP` 钉住（容器重启时 podman 以 VM `/etc/hosts` 为基底生成容器内 `/etc/hosts`，因此零容器改动）。映射表新增**可选第 6 列**记录域名，仅用于诊断核对，不参与规则生成。
3. **同层备选：VM 侧地址别名 + socat（E-ALIAS）**——若日后实测 DNAT 未被命中，改用「VM 把真实地址挂到 lo + socat 监听真实地址」，绕开 netfilter。**2026-10-20 真机 nft 路径已成立，E-ALIAS 降为纯兜底、不占实施工时**（§6.2.1）。
4. **容器侧备选 A（`NET_ADMIN` + 容器内 DNAT）**——因 Q1 已确认走 VM 侧，**不采用**；仅作为"VM 侧被策略锁死"时的退路记录（代价：改 `compose.yaml`、重建镜像、已有安装目录 compose 不会被 `install.ps1` 覆盖）。
5. **明确不选**：B（与 A 同权限但多进程多依赖）、C（LD_PRELOAD，全容器进程风险 + 需外部编译）、D（应用层覆盖，不满足"透明"）、F（redsocks/tun2socks/gost 无额外收益）。
6. **阶段 0 已完成（2026-10-20 真机）**：E1 VM 直连 = `VM-DIRECT-FAIL` ⇒ "整网段路由 + MASQUERADE"备选**彻底排除**（VM 自己无路可走）；E2 VM 只有 `nft` 无 `iptables` ⇒ `ip nat` 路径不存在，纯 nft 为唯一路径；**E3 纯 nft 手工探路 CONNECT-OK**（`priority dstnat - 1`）。剩余待验：S2（JVM）、S3（工程启动）、S7（域名），见 §10 阶段 0 清单。
7. **单一入口与配置面（R-S1）**：用户只运行 `relay.ps1`（唯一入口）、只在 `relay.json` 的 `services[]` 一处配置（由 `relay.ps1` 交互写入，不要求手改）；域名在**同一次交互**里录入，落为可选 `host` 字段，不二次询问。映射表 `relay-map.env`、VM `/etc/cadence-relay-dnat.env`、VM `/etc/hosts` 标记段全部是**派生物**，由脚本自动生成，用户不编辑（§5.6）。
8. **规则固化（R-S2）**：nft table 与其中的规则是**内核内存态**，VM 重启必丢，因此必须由既有持久化机制从**文件态**（`/etc/cadence-relay-dnat.env` + unit 文件）重放：systemd 可用时 `cadence-relay-dnat.service`（`Type=oneshot`、`RemainAfterExit=yes`、`systemctl enable`），不可用时 `wsl.conf [boot]` 监督循环每 5 秒幂等重放；**容器重启不影响**（规则在 VM 根 netns，不在容器 netns）。DNAT 目标固定取 relay 服务表里 socat 的实际 bindaddr（保证"改写后有人接"），与当前网桥 gateway 的漂移只告警、提示重跑 `relay.ps1`（§6.2 步骤 1、R20）。

## 1. 问题与目标

### 1.1 现象与链路

Spring 工程从 ibos-config-server 拉到的是 atrust 后的真实内网地址（例：`10.129.12.75:3306`）。容器内直连该地址失败，因为：

- 容器发包 → podman 网桥（`cadence_default`，网关例 `10.89.0.1`）→ WSL VM 转发 → Windows 侧 VPN；
- VPN（aTrust）**丢弃一切 NAT 转发流量**（`devbox/README.md` §2.6 "实测定论"）；
- 而容器可直接访问的，是 VM 上 socat 监听的桥接地址（例 `10.89.0.1:23306`），它经 `127.0.0.1:13306` → Windows portproxy → VPN，属于宿主发起流量，VPN 放行。

因此缺的只有一件事：**把"进程要去的真实地址"在报文层替换成"VM 上已存在的桥接地址"**。

### 1.2 "透明"的定义（本设计的硬判据）

对容器内**任意进程**（含 JVM、`podman exec` 起的 shell、构建工具、AI CLI 自身）：

| # | 要求 |
|---|---|
| T1 | 进程仍然写/用真实地址，不做任何地址换算；应用代码、启动参数、环境变量均不需要知道桥接地址 |
| T2 | 不改配置中心里的数据（只读，不写） |
| T3 | 不改工程配置文件（`application.yml`/`bootstrap.yml`/`pom.xml` 等一律不动） |
| T4 | 不改容器启动参数与镜像（主方案必须满足；备选方案允许，但要显式列出代价） |
| T5 | 容器重建、镜像升级、VM/宿主重启后无需人工干预即恢复（VM 发行版被 `podman machine rm`/`wsl --unregister` 重置除外，见 R19） |

### 1.3 成功判据（可观测）

| # | 判据 | 验证命令 |
|---|---|---|
| S1 | 容器内 `bash` 直连 `<真实IP>:<端口>` 成功（TCP 建连） | §7.1 |
| S2 | 容器内 **JVM** 直连真实地址成功（排除"只有 shell 能连"的假阳性） | §7.2 |
| S3 | Spring 工程启动到就绪，数据源/Redis/ZK 初始化无 `Connection timed out`/`Connection refused` | §7.3 |
| S4 | 容器内本地 stack 中间件（`127.0.0.1:3306`、`127.0.0.1:6379`）行为不变 | §7.6 |
| S5 | 映射之外的真实地址、以及外网访问，行为不变（无全量劫持） | §7.6 |
| S6 | 回滚后恢复原状：直连真实地址重新失败，其余一切不变 | §6.5 |
| S7 | **域名用例**：容器内以域名连接成功，且 `getent hosts <域名>` 与 `relay.json` 的真实 IP 一致（Q5） | §6.1-0.4、§7.4.1 |

### 1.4 范围

**包含**：TCP 服务（MySQL/Redis/ZooKeeper/配置中心/Kafka broker 等）；IPv4；单台 devbox 容器及其所在 `cadence_default` 网络；**域名场景**的解析判定与"域名 → 真实 IP"固定（§7.4）。

**不包含**：UDP 服务的代理（现有 relay 只有 `socat TCP-LISTEN`，无 UDP 能力，映射表也按 TCP 设计）；**面向 IPv6 目标地址**的代理（DNAT 只做 v4；域名带 AAAA 时的处理见 §7.4.5）；域名解析服务本身的重建（不自建 DNS，理由见 §7.4.3）；多宿主/多网桥拓扑；aTrust 侧配置。

## 3. 环境判定（落地前必须先跑）

### 3.1 容器内一条命令（只读探测，不改任何东西）

在目标机器的 devbox 容器里执行（`podman exec -it devbox bash` 后整段粘贴）：

```bash
set -u
echo "== 身份/权限 =="
id
sudo -n true 2>/dev/null && echo "sudo=OK" || echo "sudo=NO"
awk '/^Cap(Inh|Prm|Eff|Bnd):/{print}' /proc/self/status
cap=$(sudo grep '^CapBnd:' /proc/self/status | awk '{print $2}')
echo "NET_ADMIN(in CapBnd)=$(( (16#${cap:-0} >> 12) & 1 ))"

echo "== 工具 =="
for b in iptables iptables-legacy nft ip ss socat python3; do
  printf '%-14s %s\n' "$b" "$(command -v "$b" 2>/dev/null || echo ABSENT)"
done

echo "== netfilter 可用性 =="
sudo iptables -t nat -L -n >/dev/null 2>&1 && echo "nat-table=OK" || echo "nat-table=FAIL"
nft list ruleset >/dev/null 2>&1 && echo "nft=OK" || echo "nft=FAIL"

echo "== 加地址是否被允许 =="
sudo ip addr add 127.0.0.2/32 dev lo 2>&1 | head -1
sudo ip addr del 127.0.0.2/32 dev lo 2>/dev/null

echo "== 现实连通性 =="
timeout 3 bash -c 'echo > /dev/tcp/10.129.12.75/3306' 2>/dev/null \
  && echo "real-addr=REACHABLE" || echo "real-addr=UNREACHABLE"
gw=$(awk '$2=="00000000"{print $3; exit}' /proc/net/route); gw=${gw:-00000000}
printf 'default-gw=%d.%d.%d.%d\n' \
  "$((16#${gw:6:2}))" "$((16#${gw:4:2}))" "$((16#${gw:2:2}))" "$((16#${gw:0:2}))"
```

把 `10.129.12.75/3306` 换成用户当前报错的那个地址即可。

### 3.2 判定矩阵（按输出选路径）

| 观测 | 结论 |
|---|---|
| `NET_ADMIN(in CapBnd)=0`（预期） | 容器侧 A/B **不可行**（即使 `sudo` 成 root 也不行，cap 在容器配置里被裁剪）→ 走 **E**（主方案） |
| `NET_ADMIN=1` 但 `iptables`/`ip` 为 `ABSENT` | A/B 需先加包（镜像改 `Dockerfile` 或运行时 `apt-get`）；仍要改 compose → 只作备选 |
| `NET_ADMIN=1` 且 `nat-table=OK` | A 可行；但仍需改 compose + 镜像 → 见 §4.1 代价 |
| `nft=FAIL` / `nat-table=FAIL` 且报错含 `can't initialize iptables table` | 内核 netfilter 模块缺失 → 容器侧直接排除；VM 侧也要在 §3.3 查 |
| `real-addr=REACHABLE` | 不需要代理——先查应用的真实失败原因（端口/白名单/账号），不要继续本方案 |
| `default-gw=` 不是 `10.89.0.1` | 网桥网关已漂移：`relay.ps1 -Status` 会报 hop3，先重跑 relay setup 再谈映射 |

### 3.3 Windows / VM 侧自检（E 方案的前置）

```powershell
# 1) VM 是否运行、sudo 是否可用（默认用户通常不是 root，relay.ps1 一律用 sudo）
podman machine ssh 'id -u; sudo id -u'
# 2) VM 是否有 netfilter 工具与表（真机结果：只有 nft，无 iptables —— §11.3-E2）
podman machine ssh 'command -v iptables nft ip; iptables --version 2>&1 | head -1; nft list tables 2>/dev/null | head; nft list ruleset 2>/dev/null | grep -B1 -A3 "hook prerouting"'
# 3) 当前网桥与网关（**仅用于比对/告警**；DNAT 目标取 relay 服务表 bindaddr，见 §6.2 步骤 1）
podman network inspect cadence_default --format '{{range .Subnets}}{{.Subnet}} gw={{.Gateway}}{{end}}'
# 4) relay 是否已在跑（应有 cadence-relay@mysql 等）+ 服务表（DNAT 目标的权威来源）
podman machine ssh 'systemctl list-units "cadence-relay*" --no-pager; cat /etc/cadence-relay.env'
```

判读：

- **`iptables: command not found` 在本机是正常状态**（Fedora 44 Container Image 不带 iptables，§11.3-E2）——**不是**"无权限"，也不需要 `dnf install`（那会引入 podman machine 升级后丢失的外部依赖）。纯 nft 即可，§4.5.1/§6.2 步骤 1 已按此定稿。
- `nft list ruleset | grep -A3 'hook prerouting'` 会看到 netavark 自己的 base chain 及其 priority（标准为 `dstnat`）。**不要**改它们；本方案自建 `table ip cadence_dnat`、`priority dstnat - 1`，靠 priority 排在 netavark 之前。
- `/etc/cadence-relay.env` 是 DNAT 目标的权威来源（`name vmport bindaddr hostport`），产品化后由 `dnat_apply` 读取，不手填。

### 3.4 三类失败要分开读

| 报错 | 含义 | 处理 |
|---|---|---|
| `Permission denied (you must be root)` / `Operation not permitted` | 缺 `NET_ADMIN` | 走 E；或按 §4.1 加 cap |
| `can't initialize iptables table 'nat'` | 内核模块缺失（容器通常 `ls /lib/modules` 为空，靠宿主内核） | 容器侧排除；VM 侧通常可用（podman 自身依赖 NAT） |
| `iptables: command not found` | 只是没装二进制 | 与权限无关，别误判为"无权限" |

## 4. 方案对比

### 4.0 总表

**能力维度**

| 方案 | 落点 | 透明度 | 所需权限 | 需重启容器 | TCP / UDP | 容器重建后存活 |
|---|---|---|---|---|---|---|
| A 容器 DNAT（`nat OUTPUT`） | 容器 netns | 全进程 | `NET_ADMIN` + root | 是 | TCP；UDP 可同规则 | 否（需再应用） |
| B 容器 lo 别名 + socat | 容器 netns | 全进程 | `NET_ADMIN` + root | 是 | TCP；UDP 需换转发器 | 否 |
| C LD_PRELOAD `connect()` | 进程地址空间 | 仅动态链接进程（Go/Bun/静态二进制绕过） | 无（写 `/etc/ld.so.preload` 则需 root） | 否（仅新进程） | TCP/UDP 的 `connect` 均可见 | 需镜像/卷持久 |
| D 应用层覆盖 | 应用参数/环境 | **否**（逐应用、逐键） | 无 | 是 | 取决于应用 | 是（改启动命令） |
| E-DNAT（**推荐**） | VM root netns | 全容器全进程 | VM root（已有） | 否 | TCP（可扩 UDP） | 是 |
| E-ALIAS | VM root netns | 全容器全进程 | VM root（已有） | 否 | TCP | 是 |
| F redsocks/tun2socks/gost | 容器 netns | 全进程 | `NET_ADMIN`/`privileged` + `/dev/net/tun` | 是 | 取决于实现 | 否 |

**成本维度**

| 方案 | 额外依赖 | 故障影响面 | 可维护性（归属） | 实施体量 |
|---|---|---|---|---|
| A | 镜像加 `iptables`+`iproute2`；compose 加 `cap_add` | 仅 devbox 容器 | 中：3~4 个文件（Dockerfile/compose/relay.ps1/README） | 中 |
| B | 同上 + `socat`或自研转发器 + 监督循环（容器无 systemd，`init:true` 只做回收） | 仅 devbox 容器 | 低：要自己写守护 | 大 |
| C | 外部编译 `.so`；供应链 | **全容器进程**（坏 `.so` 会让 `podman exec` 都起不来） | 低 | 大 |
| D | 无 | 单应用 | 极低（键多、优先级不确定） | 小但重复劳动 |
| E-DNAT | VM 有 `nft`（真机已确认，§11.3-E2） | `cadence_default` 上所有容器（符合预期） | 高：并入 relay 子系统，沿用事务/自恢复 | 中（+1 映射文件 +2 子命令） |
| E-ALIAS | VM 已有 `ip`/`socat` | 同上 | 高 | 中 |
| F | 额外软件 + TUN | devbox 容器 | 低 | 大 |

### 4.1 A：容器 `NET_ADMIN` + `iptables/nft` OUTPUT DNAT

前置（三项都满足才成立）：

1. `compose.yaml` 的 `devbox` 加 `cap_add: [NET_ADMIN]`（或 `--cap-add=NET_ADMIN`，走 `podman run` 路线时）；
2. 镜像里加 `iptables`、`iproute2`（`devbox/Dockerfile:27-30` 的 apt 清单），需重建 + 重新分发镜像；
3. 容器能读到映射表（`/cadence/stack/data/relay-map.env`，见 §5）。

规则形态（幂等）：

```bash
sudo iptables -w 5 -t nat -N CADENCE-DNAT 2>/dev/null || true
sudo iptables -w 5 -t nat -C OUTPUT -j CADENCE-DNAT 2>/dev/null || \
  sudo iptables -w 5 -t nat -I OUTPUT 1 -j CADENCE-DNAT
sudo iptables -w 5 -t nat -F CADENCE-DNAT
while read -r name real_ip real_port target_ip target_port; do
  target_port=${target_port%$'\r'}
  case "$name" in ''|'#'*) continue ;; esac
  sudo iptables -w 5 -t nat -A CADENCE-DNAT -d "$real_ip/32" -p tcp --dport "$real_port" \
    -j DNAT --to-destination "$target_ip:$target_port"
done < /cadence/stack/data/relay-map.env
sudo iptables -w 5 -t nat -L CADENCE-DNAT -n -v
```

代价与坑：

- **已有安装不会被自动修好**：`install.ps1` 不覆盖已存在的 `stack/compose.yaml`（F14），用户必须手工加 `cap_add` 或按文档迁移；
- `nat OUTPUT` 上的 DNAT 依赖 conntrack 反向改写，历史上对本地生成流量有过若干边界问题——**必须**用 §7.2 的 JVM 探针实测，不能只用 shell 的 `/dev/tcp` 下结论；
- 容器 netns 若被重建（`podman rm/run`），规则全丢，需要重新应用；
- 权限面扩大：容器内任何进程都能改自己 netns 的防火墙（对已挂 `docker.sock` 的 devbox 属于边际增加，但不是零）。

### 4.2 B：容器 `NET_ADMIN` + lo 别名 IP + socat/REDIRECT

机制：`ip addr add <真实IP>/32 dev lo`，使 `connect(<真实IP>:<端口>)` 落到本地；再由监听该地址的转发器送到 `10.89.0.1:<vmPort>`。

**不选 B（作为主方案）的理由**：

- 与 A **同样的权限要求**（都要 `NET_ADMIN`），但还要额外的 `iproute2` + 转发器 + **自己写监督循环**（容器里没有 systemd，`init: true` 只回收僵尸进程）；
- 多一层进程，故障面更大（转发器挂了 → 表现为"连接被拒"，比"规则丢失"更难辨）；
- 同样的机制放到 VM 侧就变成 E-ALIAS，直接白拿 systemd `Restart=always`——没有理由在容器里重造。

### 4.3 C：无特权 `LD_PRELOAD` 改写 `connect()`

机制：编译一个 `.so` 拦截 `connect(2)`，命中映射表时改写 `sockaddr_in`；用 `/etc/ld.so.preload`（全容器）或 `LD_PRELOAD`（逐进程）加载。

**Java 下可行性**：Temurin 21 是动态链接 glibc，`java.net` 的 `NET_Connect` 最终调用 libc `connect`；`SocketChannel`、Netty 的 epoll 原生传输同样落到 libc `connect`。所以**对 JVM 是有效的**——这也是它值得评估的原因。

**坑（逐条都会咬人）**：

1. **不是全进程**：Go、Bun/Zig 等直接走系统调用，静态链接二进制完全绕过——写"全进程透明"就是错的；
2. 需要**外部编译**（镜像无 `gcc`），引入一条二进制供应链；
3. `/etc/ld.so.preload` 里放坏 `.so` → **整容器不可 exec**，只能 `podman cp` 修文件或重建容器；恢复成本极高；
4. `sudo` 的 secure-exec 会剥离 `LD_PRELOAD`（`/etc/ld.so.preload` 不受影响，但风险如 3）；
5. 只覆盖 `connect`：`getaddrinfo`（域名）、IPv6、UDP 的 `sendto` 无地址参数等都要单独处理；
6. 只对**新启动**的进程生效，已在跑的 JVM 无感知。

结论：仅当"无 VM 权限 + 不改容器参数"同时成立时才考虑；本场景 VM 权限已经存在（relay 就是这样工作的），没有必要承担 3 的风险。

### 4.4 D：应用层覆盖（Spring Cloud Config / 启动参数 / 环境变量）

机制：给每个应用加 `--spring.datasource.url=...`、`SPRING_REDIS_HOST=...` 等。

**不满足"透明"的理由**：

- 需要**逐应用、逐键**列举（数据源 URL、Redis host/port、ZK `connectString`，以及项目自定义键），键名要先从配置中心或工程里挖出来——这是"改工程配置"的变体；
- 优先级不确定：Spring Boot 命令行参数最高，但 **Spring Cloud Config 客户端默认 `override-system-properties=true`**，`-D`/系统属性可能被远端配置反覆盖；环境变量是否生效还取决于 `spring.cloud.config.override-*` 开关——**必须逐项目实测**（本设计未实测，标注为假设）；
- 多应用、多环境、多版本并存时维护成本线性增长，且新人不知道要加。

结论：只作为单项目应急（在启动命令上显式给 `--spring.datasource.url=jdbc:mysql://10.89.0.1:23306/...`），不作为通用方案。

### 4.5 E：VM 侧方案（推荐）

#### 4.5.1 E-DNAT（主方案）

**为什么成立**：容器到 `10.129.12.75` 的包本来就要经过 VM（默认路由指向 `10.89.0.1`）。在 VM 的 `nat`/`PREROUTING` 里把它 DNAT 成 `10.89.0.1:23306`（VM 本地地址）后：

```text
容器进程 connect(10.129.12.75:3306)
  → veth/网桥 → VM PREROUTING 命中 DNAT → 目标改为 10.89.0.1:23306（VM 本地）
  → 已有 cadence-relay@mysql 的 socat 接住 → 127.0.0.1:13306
  → Windows portproxy → VPN → 真实 MySQL
返回按 conntrack 反改写，客户端看到的对端仍是 10.129.12.75:3306。
```

- **零容器特权**：VM 里本来就是 root（F2）；
- **零镜像/零 compose/零工程配置改动**；
- **容器重建、升级镜像都不影响**（规则在 VM 根 netns）；
- **复用已有自恢复**：套用 `cadence-relay@*` 的 systemd/boot 兜底模式（F3）；
- 覆盖 `cadence_default` 上**所有**容器（对"任意进程"是加分，不是负担）。

**已实测通过的门槛（2026-10-20，§11.3-E2）**：目标 VM **没有 `iptables`、只有 `nft`**（Fedora 44 Container Image），因此 `ip nat` 表路径在这台机器上**不存在**——纯 nft 是唯一路径。手工探路已在真机通过：自建 `table ip cadence_dnat` + `chain prerouting { type nat hook prerouting priority dstnat - 1 ; policy accept ; }` + `dnat to <bindaddr>:<vmPort>`，容器内 `connect(10.129.12.75:3306)` 返回 **CONNECT-OK**，nft 确认 priority 显示为 `dstnat - 1`（早于标准 `dstnat`）。

因此：
- **规则形态改为纯 nft**：`dnat_apply` 写 `table ip cadence_dnat`（base chain `prerouting`，`priority dstnat - 1`），**不再**用 `ip nat` 表或 `CADENCE-DNAT` 链；§6.2 步骤 1 的实现形态随之改为 nft。
- **不再需要"路径选择标记文件"**（v1.2 §6.2.2 的 `/etc/cadence-relay-dnat-nft` 标记文件作废）：原本用它区分"走 `ip nat` 还是走自建 nft table"；现在只有一条路径，nft table 由 `dnat_apply` 幂等重建即可。
- **R-S2 的持久化机制不变但语义更简单**：nft table 是**内核态**、VM 重启即丢（与 iptables 规则同理）——所以仍需 `cadence-relay-dnat.service`（`ExecStart` 调 `dnat-apply`）在开机时**重建 table + chain + 规则**。`dnat_apply` 必须幂等：`nft add table ... 2>/dev/null || true` → `nft add chain ... || true` → `nft flush table` → 逐条 `nft add rule`。
- **回滚**：`nft delete table ip cadence_dnat`（真机已验证该命令可用，输出 `cleaned`）。

另一处实现选择：跳转规则默认**不限 `-i`**（只按 `-d <real>/32 -p tcp --dport <port>` 匹配），这样从镜像网卡转发进来的同类流量也会被改写，语义一致；若确认网桥接口名稳定（`podman network inspect` 可取），可加 `-i <网桥接口>` 收窄，属于可选加固。

**已知边界**：只对"到达 VM 的报文"生效；VM 自己 `connect(真实IP)` 走 OUTPUT，不经过这条 PREROUTING（所以 §7.5 的 VM 侧自测方式要写对，别用宿主直连做假阴性判断）。

#### 4.5.2 E-ALIAS（同层备选）

机制：VM 里 `ip addr add <真实IP>/32 dev lo`，让该地址成为**本地地址**；再为每个映射起一个 socat：`TCP-LISTEN:<真实端口>,bind=<真实IP>,fork,reuseaddr TCP:10.89.0.1:<vmPort>`。

- 完全绕开 netfilter：不存在多表顺序、conntrack、NAT 后端差异问题；
- 可直接 `ss -tlnp` 看到监听、`netstat -antp` 看到连接，排查直观；
- 代价：每个映射一个进程（沿用 `cadence-relay@` 的 systemd/boot 模式，成本已知）；地址别名要按真实 IP 维护；
- 触发条件：E-DNAT 门槛不通过；或 VM 内核/nftables 被策略锁定。

### 4.6 F：其他（不展开，仅说明为何不选）

| 候选 | 结论 |
|---|---|
| redsocks / tun2socks | 都需要 `NET_ADMIN`（redsocks 靠 iptables 重定向；tun2socks 要 `/dev/net/tun`），容器侧权限条件与 A/B 相同，却多一个常驻进程与配置面 |
| gost | `-L redirect://`/TProxy 同样依赖 iptables；作为普通端口转发器（`-L tcp://:23306`）不解决"客户端仍连真实地址"的问题 |
| `unshare -Urn` 无特权 netns | 需要内核允许非特权 user namespace + `slirp4netns`/`pasta`（镜像未装），且新 netns 看不到容器本地 stack 中间件；改造面远大于收益 |
| 共享 devbox netns 的 sidecar 加 `NET_ADMIN` | 依赖 podman-compose 对 `network_mode: service:...` 的支持（未验证），且 sidecar 仍要装 `iptables`；不如直接把规则放 VM |
| `/etc/hosts` 改写 | 只能覆盖**域名**，配置里是 IP 时无效；仅作为 §7.4 的域名补充手段 |

## 5. 映射表设计

### 5.1 数据从哪来

| 来源 | 用法 | 说明 |
|---|---|---|
| **`relay.json`（权威）** | 生成映射表的唯一输入 | 已含每个服务的 `remoteHost`/`remotePort`（真实地址）、`vmPort`、可选 `host`（域名，同一次交互录入）与 `gateway`（F4）。用户在 `relay.ps1` 里配 relay 时已经录过一遍，不重复劳动 |
| 配置中心只读查询 | 补齐未入 relay 的地址 | `curl -s "http://<config-server>:<port>/<应用名>/<profile>"`（Spring Cloud Config 端点）后用正则提取 `IP:端口` |
| 运行中应用 | 同上 | `curl -s http://127.0.0.1:<port>/actuator/env`（若开了 actuator） |
| 启动失败日志 | 最可靠的"缺了哪个" | 超时/拒绝日志里的 `host:port` |
| 工作区扫描 | 辅助发现 | 见下方命令；注意**配置中心的真实值可能不在工作区里**，扫描结果只能当线索 |
| 用户直接提供 | 兜底 | 有疑义以用户为准 |

Q3 已确认 `relay.json` 已含全部真实地址：下表其余来源只用于**发现遗漏**与异常排查，**不作为**映射表的生成输入。

发现用一次性命令（只读）：

```bash
# 工作区里的 IP:端口 线索（按出现次数排序）
grep -rhoE '([0-9]{1,3}\.){3}[0-9]{1,3}:[0-9]{2,5}' /workspace \
  --include='*.yml' --include='*.yaml' --include='*.properties' --include='*.xml' 2>/dev/null \
  | sort | uniq -c | sort -rn | head -30
```

补齐流程：发现一个未映射的 `真实IP:端口` → 用 `relay.ps1` 新增一个服务（目录项或 `custom`，服务名限 `[A-Za-z0-9_-]`）→ 重跑 setup → 映射表自动带上。**不要**手工只改映射表而不建 relay 监听：那样 DNAT 的目标端口根本没人监听。

### 5.2 为什么必须新开文件（不能扩展现有的 4 列表）

`relay-vm.sh` 在 **9 处**按四元组解析（F1），代表性写法：

```bash
while read -r name vmport bindaddr hostport; do
```

第 5 段会被 `hostport` 吃掉（变成 `"13306 额外内容"`）。后果是双向断链：

- 新起的实例：生成的 run 脚本（`:139` 同构读取）把目标拼成 `TCP:127.0.0.1:13306 额外内容`，socat 拒绝该端口写法 → 监听起不来 → `cmd_setup` 在 `wait_listener` 段 FAIL 并回滚（`:532-545`）；
- 已在跑的旧实例：`is_expected_socat`（`:103-116`）用带空格的 `want_t` 与旧进程 argv `TCP:127.0.0.1:13306` 比对 → 全部失配 → 不接管、端口仍被旧实例占用 → `die3`（`:425`/`:430`）。

改格式等于同时改 9 个解析点 + 所有测试桩的 argv 断言（F15），不划算。

因此：**现有表原样不动，新增第二个文件**。

### 5.3 映射文件格式与校验

两个位置、同一内容（一份给容器侧方案用，一份给 VM 用）：

| 位置 | 容器/VM 可见路径 | 用途 |
|---|---|---|
| `<安装目录>/stack/data/relay-map.env` | `/cadence/stack/data/relay-map.env` | A/B/C 在容器内读取 |
| VM `/etc/cadence-relay-dnat.env` | — | E 在 VM 内读取 |

选 `stack/data/` 的理由：`/cadence/stack` 是 bind mount（F13），`data/` 已在安装器 `.gitignore` 里，且不在 entrypoint 步骤 4 的模板同步清单内（F12）——不会被覆盖、不污染仓库。

格式（**5 段必填 + 第 6 段可选域名**，空白分隔，`#` 注释，CRLF 容忍）：

```text
# 由 relay.ps1 生成，勿手改。
# <name> <real_ip> <real_port> <target_ip> <target_port> [domain]
mysql 10.129.12.75 3306 10.89.0.1 23306 mysql.corp.internal
redis 10.129.20.31 6379 10.89.0.1 26379
zk1   10.129.30.11 2181 10.89.0.1 22181 zk1.corp.internal
```

第 6 段（`domain`）的定位：**只用于诊断与文档**（`-Status` 用它核对"容器内解析结果是否等于 `real_ip`"），**不参与规则生成**——DNAT 只匹配 IP，域名路径见 §7.4.2。可以省略，也可写 `-` 表示"该服务在配置里只用 IP"。来源是 `relay.json` 的可选 `host` 字段（§5.4 与 `relay.ps1` 同一问句录入），用户不直接编辑本文件。

`target_ip` 的定位（R20）：它是**生成时的网关留痕**，用于与 relay 服务表的 bindaddr、与当前网桥 gateway 做三方比对并报漂移。**DNAT 规则的实际目标取自 relay 服务表 `/etc/cadence-relay.env` 的 bindaddr 列**——那才是 socat 真正在监听的地址；写死或改指别处都会把包送到无人监听处（详见 §6.2 步骤 1）。保留该字段的价值是审计（表是给哪个网桥生成的）、离线诊断与三方交叉校验。

为什么不是"第 6 列换成域名、由消费端自己解析"：
- 解析结果取决于**容器视角**，而消费端（VM 侧脚本）解析出来的是 VM 视角，两者可能不一致（split-horizon）——用 VM 的解析结果去反推容器行为，正是要避免的错误来源；
- 真实地址必须由人确认、可审计（Q3 已确认 `relay.json` 含全部真实地址），不能让脚本"猜"。

校验规则（生成端与消费端**都要**做；除第 3 条为告警外，任一条不满足直接报错，不静默跳过）：

1. `name` 匹配 `^[A-Za-z0-9_-]+$`；`real_ip`/`target_ip` 是合法 IPv4 点分十进制；端口 `1..65535`；
2. `(real_ip, real_port)` 唯一（同一真实地址端口不能有两个目标）；
3. `target_ip` 与 relay 服务表的 bindaddr、与当前网桥 gateway **不一致时告警不阻断**（R20）：`dnat_apply` 一律按**服务表 bindaddr**（socat 实际监听地址）写规则；`target_port` 同理一律取服务表的 vmPort（映射表第 5 列只作比对，与真实端口不一致同样告警）。`-Status` 打印"映射表 target_ip=X / 服务表 bindaddr=Y / 当前 gateway=Z（或 bindaddr 不在网卡）"提示重跑 `relay.ps1`；**绝不**把 `target_ip`/`target_port` 当死值写进 DNAT 目标；
4. 行尾 `\r` 剥离（沿用 `read_env` 的 `${var%$'\r'}` 风格）；
5. 第 6 段若存在：匹配 `^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?$` 或等于 `-`；**不得**是 IP 字面量（域名段写 IP 视为配置错误，提示改用 `real_ip` 段）。

### 5.4 生成与分发（幂等）

在 `relay.ps1` 的 `Invoke-Setup` 里追加一步。**生成时机（按现实现锚点）**：`Invoke-Setup` 的既有执行序是 前置自检（远端可达，`:429-435`）→ 陈旧服务 portproxy 清理（`:437-442`）→ `$gw = Get-BridgeGateway`（`:444`）→ `$ctr = Get-DevboxContainer`（`:446`）→ portproxy 幂等写入（`:448-456`）→ 服务表/对账表渲染（`:458-469`）→ `machine cp`（`:470-475`）→ `ssh mv`（`:476-479`）→ `relay-vm.sh setup`（`:481-489`）→ 容器探活（`:491-496`）→ `relay.json` 落盘（`:498-500`）。映射表插入点必须在 **`:446` 之后、`:470` 之前**（与 `$ctr` 探测、portproxy 写入无依赖，放在 `:458` 服务表渲染同处最自然），直接用内存中的 `$services` 与 `$gw` 渲染——此时 `relay.json` 尚未落盘（它到 `:500` 才写），不能读它当数据源。分发顺序：先 `cp` 映射表并 `mv` 到 `/etc/cadence-relay-dnat.env`，再执行 VM `setup`（其末尾调用 `dnat_apply`，见 §6.2）。唯一硬约束是"早于 `machine cp`/`setup`"；因为 `target_ip` 与 DNAT 目标（服务表 bindaddr）同源于本次 `$gw`，插入点在 `:446` 之后的位置微调不改变语义。

`relay.json` 的 `services[]` 增加**可选**字段 `host`（域名，可为空），落盘形态与既有字段并列（`remoteHost`/`remotePort` 语义不变）。地址仍走 `Test-AddrFormat`（`^(\d{1,3}\.){3}\d{1,3}:\d{2,5}$`）校验，但**只校验第一段**：域名由 `Split-AddrInput` 先按空白切分、再单独交给 `Test-HostName`（F19）：

- **同一次交互录入（R-S1）**：地址问句从 `IP:端口` 扩展为 `IP:端口[ 域名]`，域名是同一行的可选第二段；不写即纯 IP 服务。修改已有服务时同一问句也接受新域名（回车=保持原值）——**没有第二次询问，也不要求用户手改 JSON**。
- **四个录入点必须全部改走 `Split-AddrInput`**（按现实现逐个点名；漏一个即为功能不闭合）：
  - 修改保留项：`relay.ps1:298-307`（`$val` 先经 `Split-AddrInput $val $o.host`，再把 `addr`/`host` 分别传给 `New-Service`/`New-ServiceWithHostPort`）；
  - `-MySQL`/`-Redis` 参数：`:320-323`（参数保持 `IP:端口` 纯形态、**不解析域名**；但覆盖同名服务时须把旧 `host` 传给 `New-Service`，否则"参数更新"会静默丢域名）；
  - 自定义新增：`:350-353`；
  - 目录新增：`:361-364`。
- **旧值保留与清空**：`New-Service`（`:170-181`）/`New-ServiceWithHostPort`（`:183-201`）增加可选 `$host` 参数并写入返回对象；`Collect-Services` 重建旧服务对象时**必须带上 `host`**（现实现只复制 5 个字段，`:215-220`，会丢域名）；落盘仅在非空时写 `host` 键，旧 `relay.json` 无该键等价于"未录入"（读取按 `$_.PSObject.Properties['host']` 判空，不假定键存在）。**清空语义**：域名段输入 `-` 或 `none` 表示显式清空（`Split-AddrInput` 消费；`Test-HostName` 仍不接受 `-`）——否则"回车=保持原值 + 不接受 `-`"会使用户永远无法删除已录入的域名。
- **校验**：`host` 走独立校验（§5.3 第 5 条：合法域名，不得是 IP 字面量）。`Test-HostName` 的拒绝面必须覆盖：IP 字面量、空串、含空白、以 `.`/`-` 开头或结尾、连续点、超长（整体 >253、单标签 >63）、`-`；允许大写但**落盘前统一小写**（保证"同一输入字节级一致"的幂等性）。含 `_` 的内网名不在允许集（RFC 952/1123）——若现场确有此类域名，应显式放宽规则，而不是让用户看到不明所以的失败。

```powershell
function Test-HostName($s) {
  if (-not $s) { return $false }
  $s = "$s".Trim()
  if ($s.Length -gt 253) { return $false }
  # 域名位写 IP 字面量视为配置错误（§5.3 第 5 条）
  if ($s -match '^(\d{1,3}\.){3}\d{1,3}$') { return $false }
  if ($s -notmatch '^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?$') { return $false }
  if ($s -match '\.\.') { return $false }                       # 连续点
  foreach ($lab in ($s -split '\.')) { if ($lab.Length -gt 63) { return $false } }
  return $true
}

# 地址问句的唯一输入形态："IP:端口" 或 "IP:端口 域名"（域名可选，同一问句）
# 域名段为 "-" / "none" 表示显式清空（区别于回车=保持原值）
function Split-AddrInput($raw, $oldHost) {
  $raw = "$raw".Trim()
  $tok = @($raw -split '\s+', 2 | Where-Object { $_ -ne '' })
  $addr = if ($tok.Count -ge 1) { $tok[0] } else { '' }
  if (-not (Test-AddrFormat $addr)) { Die "地址格式应为 IP:端口[ 域名]，收到：$raw" }
  $host = $oldHost
  if ($tok.Count -gt 1) {
    $h = $tok[1].Trim()
    if ($h -in @('-', 'none')) { $host = $null }
    elseif (-not (Test-HostName $h)) { Die "域名格式不合法：$h（留空=保持原值；- 或 none=清空）" }
    else { $host = $h.ToLowerInvariant() }
  }
  return @{ addr = $addr; host = $host }
}
```

映射表生成（注意取 `remoteHost`/`remotePort`；`target_ip` 写生成时的 `gateway`）：

要点：

- **必须无 BOM**：`Set-Content -Encoding utf8`（WinPS 5.1）会写 BOM，首行的 `name` 会变成 `\ufeffmysql`，bash 侧校验直接失败。沿用仓库已有做法 `-Encoding ascii`（`relay.ps1:462` 写服务表、`:469` 写对账表都是这个写法）；
- **原子写**：先写 `.tmp` 再 `Move-Item -Force`，避免半截文件被消费（上面的代码即此形态）；
- **幂等**：同一份输入（服务清单 + gateway）重跑生成字节级一致；不追加、不去重表；
- **`host` 不参与 DNAT 规则生成**：DNAT 只按 `real_ip`/`real_port` 匹配；`host` 供 `-Status` 核对解析结果，并被延后的 `hosts_apply`（§6.2 步骤 2）消费；
- **`-List` 不新增域名列**（若确实要加，必须保证任何一行 ≤100 字符）：`tests/devbox/test_relay.py:724-725` 对 `-List` 输出有"每行 ≤100 字符"的钉住断言，域名列最容易踩这条；
- **失败语义**：映射文件写失败 → 按现有 `Invoke-Setup` 的失败路径处理（`Undo-Portproxy` + `Die`），因为此时 DNAT 目标也不该存在。注意 VM 侧 `/etc/cadence-relay-dnat.env` 与 `/etc/cadence-relay.env` 采用**同一落盘模式**（先 `cp` 到 `/tmp`、再 `mv` 到 `/etc`，均在 `setup` 之前），而 `rollback_setup` 只快照 `RUN_SCRIPT`/`UNIT_TEMPLATE`/`BOOT_SCRIPT`/`OLD_UNIT`（`relay-vm.sh:438`）、**不含两张 env 表**——因此 setup 失败时残留是"env 停在新意图、`relay.json` 停在旧意图"。这不是本方案新增的风险（服务表今天已如此，见 §12-A），且 `dnat_apply` 只在 `setup` 末尾执行、目标取自同一份服务表，不会出现"规则指向无人监听"的额外风险；属于已知遗留语义，如需彻底消除应另立变更做 env 的事务化。

四份文件各自的职责，避免混淆：

| 文件 | 段数 | 谁写 | 谁读 | 用途 |
|---|---|---|---|---|
| `/etc/cadence-relay.env`（VM） | 4 | relay.ps1 | relay-vm.sh | socat 监听表（**不动**） |
| `/etc/cadence-relay-dnat.env`（VM） | 5+1 | relay.ps1 | relay-vm.sh | 真实地址 → 桥接地址映射（DNAT） |

### 5.6 用户可见的单一入口与配置面（R-S1）

**硬约束**：用户只运行一个脚本、只在一处配置；映射表是派生物，**不得**要求用户再配置第二处；域名也必须在同一次交互里录入。

| 层 | 谁操作 | 形态 / 位置 | 用户是否直接接触 | 职责与边界 |
|---|---|---|---|---|
| 用户入口 | 用户 | `devbox\relay.ps1`（Windows PowerShell） | **是（唯一）** | 所有动作的唯一入口：`setup` / `-Status` / `-List` / `-Teardown`；对 VM 的 `machine cp` + `ssh 'sudo bash ...'` 全部由它发起 |
| 配置来源 | 用户在同一次交互中录入 | `<安装目录>\relay.json` 的 `services[]`（`name`/`remoteHost`/`remotePort`/`hostPort`/`vmPort`/可选 `host`）+ `gateway` | **是（唯一配置面）** | 用户意图的唯一真相；域名与地址在**同一问句**录入；新增/修改/删除都靠重跑 `setup`；不要求手改 JSON |
| 派生物 | `relay.ps1` 自动生成 | `stack/data/relay-map.env`、VM `/etc/cadence-relay-dnat.env`、VM `/etc/hosts` 标记段 | 否（只读诊断，**不编辑**） | 每次 `setup` 全量重写、幂等；内容完全由 `relay.json` + 运行时事实推导 |
| VM 侧执行 | `relay-vm.sh` | `/usr/local/bin/relay-vm.sh`：`setup` / `status` / `teardown` / `dnat-apply` / `dnat-flush` | 否（用户不登录 VM） | 由 `relay.ps1` 经 `machine cp` + `ssh 'sudo bash ...'` 以 root 自动调用；systemd/boot 在 VM 内独立重放（§6.2 步骤 3） |

配套规则：

- **唯一入口判定**：新增/修改/删除服务、录域名、查状态、拆除，全部只经 `relay.ps1`。README 与设计文档不提供"让用户手改 `relay-map.env` 或 VM 文件"的常规路径——手工命令只出现在 §6.1 阶段 0 验证与排障。
- **域名同一次录入**：地址问句为 `IP:端口[ 域名]`（§5.4）；不产生第二次询问，也不需要二次编辑。阶段 0 的解析判定只决定"是否需要 `/etc/hosts` 钉住"，**不回写配置**（§9.2 Q6 已按此修订）。
- **派生物不承载用户意图**：派生物与 `relay.json`/运行时事实冲突时，以后者为准（如 DNAT 目标一律取 relay 服务表的 bindaddr 与 vmPort，映射表的 `target_ip`/`target_port` 只作比对，见 §6.2 步骤 1）。
- **失败即 setup 失败**：任一派生步骤失败都走既有回滚（`Undo-Portproxy` + `Die`），不留半套配置。

#### 6.1-0.3 VM 侧加 DNAT（纯 nft；真机已验证形态，2026-10-20）

**为什么走文件而不是命令行**：`nft add chain` 的 `{ type nat hook prerouting priority ... ; }` 规格含空格与分号，经 `podman machine ssh` 的单引号 → Windows → bash 传递会被吃掉引号而语法报错；且 `Set-Content` 写出的 CRLF 被 nft 拒绝（`unexpected CRLF line terminators`）。**唯一可靠形态：写 `.nft` 文件（显式 LF）→ `machine cp` → `nft -f`**。

```powershell
# ① 规则文件（显式 LF；nft 拒绝 CRLF）
$s = @'
table ip cadence_dnat {
  chain prerouting {
    type nat hook prerouting priority -101; policy accept;
```

实施顺序（每步都有验收与回滚，可独立提交）：

**步骤 1：`relay-vm.sh` 规则应用（`dnat-apply` / `dnat-flush`）**

- 改动：`read_dnat_env` + `dnat_apply` + `dnat_flush` + 子命令接线；**实现形态为纯 nft**（目标 VM 无 `iptables`，§11.3-E2；真机已验证，§11.3-E3）。
- **规则形态**（真机实测通过的形态，§6.1-0.3）：

  ```nft
  table ip cadence_dnat {
    chain prerouting {
      type nat hook prerouting priority -101; policy accept;
      ip daddr 10.129.12.75 tcp dport 3306 dnat to 10.89.0.1:23306
    }
  }
  ```

  即：自建 `table ip cadence_dnat` + base chain `prerouting`（`type nat hook prerouting priority -101`，`nft list` 显示为 `priority dstnat - 1`，早于标准 dstnat ⇒ 不会被 netavark 抢先）。
- **生成方式：nft 规则文件，不是命令行拼接**。`dnat_apply` 在 VM 内**写文件**再 `nft -f`：
  1. 写 `/tmp/cadence-dnat.nft`（**LF 行尾**——nft 拒绝 CRLF，实测报 `unexpected CRLF line terminators`；用 `printf '%s\n'` 逐行追加天然是 LF，勿用会产出 CRLF 的写法）；
  2. `nft delete table ip cadence_dnat 2>/dev/null || true`（清残留，保证可重复）；
  3. `nft -f /tmp/cadence-dnat.nft`；
  4. `rm -f /tmp/cadence-dnat.nft`。

  **为什么不用 `nft add chain ... '{ type nat hook ... }'` 命令行**：该规格含空格与分号，经 `podman machine ssh` 的单引号 → Windows → bash 传递会被吃掉引号而语法报错（真机踩过）。**在 VM 内生成文件则无此问题**（不跨 Windows 引号层）。
- **幂等**：每次 `dnat_apply` 都"删表 → 建表 → 逐条加规则"，天然幂等（第二次输出与第一次字节级一致）。boot 循环每 5 秒调用一次的成本是"一次 `nft -f`"，可接受。验收：连跑两次 `nft list table ip cadence_dnat` 输出一致。
- **DNAT 目标取"socat 实际监听地址"**（不是现查 gateway）：DNAT 的目标必须是**有 socat 在监听**的地址，否则包被改写后无人接收。因此每个映射的 `target_ip` 取自既有服务表 `/etc/cadence-relay.env` 的 **bindaddr 列**（`relay.ps1:461` 写入的就是 `$gw`，`relay-vm.sh` 用它 `bind=` 给 socat 监听）；`target_port` 取同一行的 vmPort。两表按 **服务名**关联。

  ```bash
  # 从既有服务表取该服务的 socat 监听地址（权威来源）
  bind=$(awk -v n="$name" '$1==n{print $3; exit}' /etc/cadence-relay.env)
  vmport=$(awk -v n="$name" '$1==n{print $2; exit}' /etc/cadence-relay.env)
  ```

  这样 DNAT 目标与 socat 监听**恒等**，不需要在 VM 内跑 `podman network inspect`（也避免 VM 内 podman CLI 路径/就绪时序问题）。真机数据（§11.3-E4）：`mysql 23306 10.89.0.1 13306` / `redis 26379 10.89.0.1 16379` / `mysql_log 23307 10.89.0.1 13307`。
- **gateway 漂移只告警、不改目标（R20）**：DNAT 目标既然是 socat 的 bindaddr，gateway 变化后 **relay 本身已经失效**——`cmd_setup` ① 段在 bindaddr 不在本机网卡时直接 die（`relay-vm.sh:367-374`），`cmd_status` 把同一条件判为 FAIL（`:583-587`），socat 实例被 systemd 重启时 `bind=<旧地址>` 也起不来。此时无论 DNAT 指旧 bindaddr 还是指新 gateway **都连不通**（前者发往已不属于本机的地址被丢弃；后者到达新网关但无人监听），差别只是"超时"还是"拒绝"。选择 bindaddr 不是因为"更糟/更好"，而是三条硬性质：

  1. 成功态下"改写后有人接"恒成立（目标 = socat 真实 bind 地址）；
  2. 规则内容不随运行时事实漂移（否则同一条 `-S` 输出会在漂移前后不同，违背 R-S2"规则不因重启改变"）；
  3. 失败可定位：规则、`-Status`、告警指向同一地址，且告警直接给出"重跑 relay.ps1"。

  `dnat_apply` 在写规则前做三方比对：

  | 比对 | 处置 |
  |---|---|
  | 映射表 `target_ip`（及第 5 列 `target_port`） vs 服务表 bindaddr/vmPort | 不一致 → 告警"映射表与 relay 服务表不一致，重跑 relay.ps1"，**按服务表 bindaddr/vmPort 写规则**（socat 在哪就指向哪） |
  | 服务表 bindaddr 是否仍在本机网卡（`ip -o addr`，与 `cmd_setup:370`、`cmd_status:586` 同一判定） | 不在 → 告警"bind=X 不在本机网卡：网桥已重建/网关漂移，relay 通道需重跑 relay.ps1"，**仍按 bindaddr 写规则**并继续（规则本身自洽） |
  | 当前 gateway（可选诊断） | `podman network inspect` 读到且 ≠ bindaddr → 在告警里追加"当前 gateway=Y"；**读不到就跳过这一句** |

  漂移判定**以"bindaddr 是否仍在本机网卡"为主判据**（与既有 `cmd_setup`/`cmd_status` 同逻辑、零新依赖）；`podman network inspect cadence_default --format '{{range .Subnets}}{{.Gateway}}{{end}}'`（与 `relay.ps1` 的 `Get-BridgeGateway`，`:389-393` 同命令）只作诊断增强——VM 内 podman CLI 是否可用、时序是否就绪均未验证（§11.4-7），不能让它承载主判定，否则"读不到就跳过"会让漂移在实机上永远不告警。
- **绝不写空目标**：服务表里查不到该服务名（bindaddr 为空）→ **该条不写规则**，打印 `[错误] <name>: 服务表缺该服务，跳过`，**其余条目照写**；映射表缺失/无有效行、或**全部条目都缺** → `exit 1`（systemd `Restart=on-failure` 会再试；boot 循环 5 秒后再来）。部分缺失时仍 `exit 0`：那属配置/生成期错误、重试不自愈，靠日志与 `-Status` 暴露（与"失败隔离"一致，§6.4）。
- **`read_dnat_env` 校验**（生成端之外的第二道）：5 或 6 段（4 段视为格式错误并 die，防止误把服务表喂进来）、行尾 `\r` 剥离、`name` 唯一、`(real_ip, real_port)` 唯一、端口 `1..65535`；`#` 注释与空行跳过。
- **`setup` 内调用语义**：`cmd_setup` ⑥ 验证通过后、`rm -rf $SNAP_DIR`（`:546`）之前调用 `dnat_apply`；其非 0 退出**不回滚 relay**（socat 侧已成功，DNAT 是附加能力），只 `log` 告警并由 `status` 暴露——回滚 relay 会连带丢掉已可用的通道。
- `dnat_flush`：`nft delete table ip cadence_dnat 2>/dev/null || true`（真机已验证该命令可用）；只动自有表，幂等。
- 回滚：`relay-vm.sh dnat-flush`；代码回退上一提交。

**步骤 3：持久化（R-S2）与重启语义**

先定性四件事：

- iptables 规则是**内核内存态**：VM 关机/重启即消失，必须从**文件态重放**；
- `/etc/cadence-relay-dnat.env` 是**普通文件态**：写在 VM 发行版磁盘上，跨 `podman machine stop/start`、跨 WSL/Windows 重启存活；
- `/etc/hosts` 标记段**不是可靠文件态**：WSL 默认在每次启动时重新生成 `/etc/hosts`（`/etc/wsl.conf` 的 `generateHosts`，默认 true），标记段可能被抹掉——因此它必须由 unit / boot 循环里的 `hosts_apply` 在每次启动后重放（R16），而不是假设它留在磁盘上；
- **容器重启与本规则无关**：规则在 VM 根 netns，不在容器 netns；`podman restart devbox`、compose up/down、容器重建都不影响它。

systemd 可用（沿用既有 `systemctl is-system-running` ∈ {running,degraded} 的判定）→ 新增单元并 `enable`：

```ini
# /etc/systemd/system/cadence-relay-dnat.service
[Unit]
Description=cadence relay DNAT rules (idempotent apply from /etc/cadence-relay-dnat.env)
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=0

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/bash /usr/local/bin/relay-vm.sh dnat-apply
ExecStop=/bin/bash /usr/local/bin/relay-vm.sh dnat-flush
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

- `dnat-apply` 内部顺序执行 `dnat_apply`，随后调用 `hosts_apply`（延后项；未实现时 no-op）——两段互不阻断，hosts 失败只告警。
- **`/bin/bash` 前缀是必须的，不是风格选择**：`podman machine cp` 不保证保留可执行位，仓库自身也从不直接 exec 该脚本——`relay.ps1:481`/`:542`/`:579` 一律 `sudo bash /usr/local/bin/relay-vm.sh ...`；只有 `write_run_script`（`relay-vm.sh:125-144`，其中 `:143` 显式 `chmod +x`）生成的 `$RUN_SCRIPT` 才被 unit 直接执行。因此写 `/bin/bash /usr/local/bin/relay-vm.sh dnat-apply`（Fedora 基底 `/bin` → `/usr/bin`，`/bin/bash` 必存在）；若改走"生成可执行脚本"模式，必须同时补 `chmod +x`、`SNAP_FILES` 快照与 teardown 清理，收益为零。
- **`Type=oneshot` + `Restart=on-failure` 的组合合法，但 v1.1 给的理由不成立**：`systemd.service(5)` 只禁止 oneshot 配 `Restart=always`/`on-success`（"For Type=oneshot, Restart=always and Restart=on-success are not allowed"），`on-failure` 自 v244 起允许，且与 `RemainAfterExit=yes` 组合即官方 "stoppable oneshot" 形态。但按步骤 1，读不到 gateway **已改为非致命**（只跳过一句诊断），`dnat_apply` 不存在"等网桥就绪"的失败面；`Restart=on-failure` 现在只兜"nft 尚未就绪/映射表短暂缺失"，保留无害，但**不得再声称它兜 gateway 就绪**。前提是 VM 的 systemd ≥244（podman machine 的 Fedora 基底满足，仍建议留证 `systemctl --version`）。
- **顺序约束**：`After=network-online.target` 可保留，但既有每服务单元用的是 `After=network.target`（`relay-vm.sh:150`）；WSL 里 `network-online.target` 没有 wait-online 保证，不能当"网关就绪"用——就绪性由 `dnat_apply` 的幂等与重试兜底。
- **所有权（谁写 / 谁 enable / 谁清理，文档必须写死）**：单元由 `relay-vm.sh` 在 `cmd_setup` ④ 段（快照之后、`daemon-reload` 之前，`relay-vm.sh:437-470`）用新增的 `write_dnat_unit()` 写出；该文件必须登记进 `SNAP_FILES`/`NEW_FILES`，且 `SNAP_ENABLED`/`SNAP_ACTIVE` 要纳入 `cadence-relay-dnat`（否则回滚后单元留成 enabled）。⑥ 段（`:511-527`）执行 `systemctl enable --now cadence-relay-dnat`，新 enable 记入 `NEW_ENABLED` 供 `rollback_setup` 撤销。**`cmd_teardown` 的 rm 清单（`:633`）必须追加** `$DNAT_UNIT` 与 `/etc/cadence-relay-dnat.env`，并先 `systemctl disable --now cadence-relay-dnat`——否则下一次开机会被 unit 重放回来，"对称拆除"（§6.5）与 R19 都不成立。
- **ExecStop 语义**：`RemainAfterExit=yes` 使 `systemctl stop`/关机走 `ExecStop=dnat-flush`；规则被清后不会自动重建，直到下一次 start/开机——这正是"stop 即失效"的预期语义。`ExecStop` 失败不改变单元状态（systemd 只记警告），与 `dnat_flush` 全 `|| true` 匹配。
- **`/etc/cadence-relay-dnat.env` 缺失时 `dnat-apply` 必须 `exit 1`** 并打印"映射文件缺失，重跑 relay.ps1"（供 `-Status` 判定，R19），不得静默 `exit 0`。

systemd 不可用（既有 boot 兜底模式）→ 复用同一个监督循环：

- **不新增第二条 `[boot] command`**（`hook_wslconf` 只允许自有钩子且拒绝外来 `[boot]` 段）；在 `write_boot_script` 生成的循环体里，每轮先执行一次 `/usr/local/bin/relay-vm.sh dnat-apply >/dev/null 2>&1 || true`，再接原有 5 秒巡检。
- 步骤 1 的幂等比对保证"规则已正确"时每轮只多一次 `iptables -S`，成本可忽略；网桥晚就绪时下一轮自然补上。

文件态与重置边界：

#### 6.2.2 纯 nft 路径的实现细节（主路径，取代 v1.2 的"ip nat / nft 双路径"）

> **本节在 2026-10-20 真机实测后重写**：目标 VM 无 `iptables`（§11.3-E2），`ip nat` 路径不存在，纯 nft 是**唯一**路径。因此 v1.2 设计的"标记文件 `/etc/cadence-relay-dnat-nft` 决定走哪条路径"**作废**——只有一条路径，不需要选择依据。nft table 由 `dnat_apply` 幂等重建（删表 → 建表 → 加规则）。

**为什么自建 table 而不用 netavark 的表**

netavark 自建的 nft table 里，base chain 挂在 prerouting 钩子上，`priority dstnat`（-100）。我们自建 `table ip cadence_dnat`，base chain 用 `priority -101`（`nft list` 显示 `dstnat - 1`）——**同 hook 的 base chain 跨 table 按 priority 升序**，数值更小的先执行，因此我们的 DNAT 一定在 netavark 之前生效，顺序变成确定性的（真机已验证，§11.3-E3）。

**规则文件形态（`dnat_apply` 在 VM 内生成）**

```nft
table ip cadence_dnat {
	chain prerouting {
		type nat hook prerouting priority -101; policy accept;
		ip daddr 10.129.12.75 tcp dport 3306 dnat to 10.89.0.1:23306
		ip daddr 10.129.20.31 tcp dport 6379 dnat to 10.89.0.1:26379
	}
}
```

- **LF 行尾**：nft 拒绝 CRLF（实测报 `unexpected CRLF line terminators`）。VM 内用 `printf '%s\n'` 逐行写天然是 LF。
- **在 VM 内写文件**：绕开 Windows → `podman machine ssh` 的引号层（`{ type nat hook ... }` 里的空格与分号会被吃掉引号，真机踩过）。产品化代码运行在 VM 内，不经 Windows，无此问题。
- **幂等流程**：`nft delete table ip cadence_dnat 2>/dev/null || true` → 写文件 → `nft -f <file>` → 删临时文件。
- **回滚**：`nft delete table ip cadence_dnat`（真机已验证，输出 `cleaned`）。

**查看 netavark 的表与优先级（排障用）**

```bash
# VM 内（root）
nft list tables                                     # 例：table ip netavark / table ip cadence_dnat
nft list ruleset | grep -B1 -A3 'hook prerouting'   # 每个 base chain 的 type / hook / priority
nft list table ip netavark 2>/dev/null || true      # 名称随 podman 版本变化，按实际输出读
```

**验收**


### 7.4 域名场景（Q5 已确认存在）

#### 7.4.1 容器内由谁解析

链路（依据 F16–F18）：

```text
应用 / getaddrinfo
  → /etc/nsswitch.conf  hosts: files dns
      ├─ files：容器 /etc/hosts（podman 生成，以 VM 的 /etc/hosts 为基底）
      └─ dns  ：/etc/resolv.conf 的 nameserver = 网桥网关（例 10.89.0.1）
                 → aardvark-dns（监听网关 :53，F17）
                     ├─ 容器名/别名 → 权威应答
                     └─ 其余（含公司域名）→ 转发上游：
                           VM /etc/resolv.conf → Windows（aTrust 适配器）DNS
```

判定命令（**容器内**执行）：

```bash
cat /etc/resolv.conf
grep '^hosts' /etc/nsswitch.conf
getent hosts <域名>            # 前几条（含 IPv4）
getent ahosts <域名>           # 全部 A/AAAA，用于发现 AAAA 干扰
python3 -c 'import socket,sys; print(socket.getaddrinfo(sys.argv[1], int(sys.argv[2]), proto=socket.IPPROTO_TCP))' <域名> <端口>
```

如何判定"解析结果是否为真实 IP"：

1. 期望值取自 `relay.json`（`relay.ps1 -List` 的"远端地址"列即真实 IP:端口）；
2. `getent hosts <域名> | awk '{print $1}' | sort -u` 的输出与之逐项比对；
3. 一致 → 解析没问题，DNAT 自动接管（§7.4.2）；
4. 不一致或为空 → 走 §7.4.3 / §7.4.4。

补充：`python3` 的 `socket.getaddrinfo` 在 Linux 上与 JVM 走同一条 libc 解析路径，可作为"Java 视角"的代理；若项目显式配置了 `sun.net.spi.nameservice` 自定义解析器，则以项目行为为准（罕见）。

#### 7.4.2 DNAT 只匹配 IP——域名是怎么被接管的

```text
应用 connect("mysql.corp.internal", 3306)
  → getaddrinfo 得到 10.129.12.75                     （解析：§7.4.1）
  → TCP SYN 目的地址 10.129.12.75:3306
  → VM PREROUTING 命中 -d 10.129.12.75/32 --dport 3306 → DNAT → 10.89.0.1:23306
  → 既有 socat → 127.0.0.1:13306 → portproxy → VPN → 真实 MySQL
```

结论：**域名不需要任何额外规则**，只需要保证解析结果是映射表里的真实 IP。只要解析正确，**用域名写与用 IP 写完全等价**；解析不正确时，加再多 DNAT 规则也没用（目的 IP 不匹配）。这也是 §5.3 里第 6 列只做诊断、不参与规则生成的原因。

#### 7.4.3 域名 → 真实 IP 的映射放哪（候选对比）

| 方案 | 落点 | 容器重建后 | 需要改什么 | 生效时机 | 评价 |
|---|---|---|---|---|---|
| **A. VM `/etc/hosts` 标记段（推荐）** | VM | 容器重建存活（每次容器启动 podman 以 VM hosts 为基底重新生成，F18）；VM 重启后由 `hosts_apply` 重放（R16） | 只改 VM（Q1 已允许） | 容器重启后 | 容器/镜像零改动；与 relay 子系统同源；可幂等增删 |
| B. compose `extra_hosts` | 容器 | 存活（声明在 compose） | 改安装目录 `stack/compose.yaml`（`install.ps1` 不覆盖，F14） | 容器重建后 | 声明式、明确；但属容器侧改动，且要用户改自己那份 compose；`podman run` 路线还得写 `--add-host` |
| C. entrypoint 注入 | 镜像/容器 | 存活 | 改镜像 entrypoint（新增第 7 步） | 容器启动 | **不选**：动镜像 + 破坏 6 步契约（F11） |
| D. 容器内手改 `/etc/hosts` | 容器 | **丢失** | 无 | 立即 | 仅用于现场排查；podman 在容器（重）启动时会重写 |
| E. VM 自建 DNS 服务 | VM | 存活 | 安装/配置 resolver，改 redirect | 立即 | **不选**：网关 `:53` 已被 aardvark 占用（F17），容器 resolv.conf 只指向它；截流会连带破坏容器名解析，且 DNS 是 UDP（本方案 DNAT 只做 TCP） |

**推荐 A**，理由：

1. 与 Q1 决策一致（只改 VM 侧），容器与镜像零改动；
2. 容器每次启动都会用 VM `/etc/hosts` 作基底重建自己的 hosts（F18），**不需要在容器内落任何东西**，也不需要 compose 变更；
3. 产物与其他 relay 产物同源（`relay-vm.sh` 在 VM 内幂等维护），`-Teardown` 可对称清理；
4. 只影响被点名的域名，不碰 DNS 链路本身。

**代价（必须写明）**：新增/修改域名后要**重启 devbox 容器**（`podman stop devbox` + `podman start devbox`）才会进入容器 hosts——这是该方法唯一的运维动作。

#### 7.4.4 推荐落地：VM `/etc/hosts` 标记段（命令级）

**只在 §7.4.1 判定"解析不到真实 IP / 解析到错 IP"时才做**；解析正确时不要加，避免无谓的地址固定。

本节命令是**阶段 0 验证与排障用**；产品化后由 `hosts_apply` 从 `relay.json` 的可选 `host` 字段自动生成（§6.2 步骤 2，延后项），**用户不需要手工编辑 VM 文件**（R-S1）。下面的手工步骤同时定义了 `hosts_apply` 必须满足的语义（幂等、只动自有标记段、写入真实 IP）。

```bash
# 在 VM（podman machine）内以 root 执行
# 1) 看现状（是否已有标记段）
grep -n 'cadence-relay-dnat' /etc/hosts || echo 'no-marker'

# 2) 幂等写入：删旧标记段 → 追加新段（只动自己的行）
python3 - <<'PY'
import pathlib
p = pathlib.Path('/etc/hosts')
begin, end = '# BEGIN cadence-relay-dnat', '# END cadence-relay-dnat'
out, skip = [], False
for line in p.read_text().splitlines():
    s = line.strip()
    if s == begin: skip = True; continue
    if s == end:   skip = False; continue
    if not skip: out.append(line)          # 非自有行原样保留（含空行）
while out and not out[-1].strip(): out.pop()   # 只裁剪尾部空行
out += [begin, '10.129.12.75 mysql.corp.internal   # cadence-relay:mysql', end]
p.write_text('\n'.join(out) + '\n')
PY

# 3) 核对
grep -A3 'BEGIN cadence-relay-dnat' /etc/hosts
```

说明：

- 用 `python3` 而非 `sed -i` 是为了**幂等**且**不动别人的行**（`/etc/hosts` 可能由系统管理）；`relay-vm.sh` 里用 bash + 临时文件实现等价逻辑即可；
- 写入的是**真实 IP**，绝不是桥接地址（指向桥接地址会让应用 `Host`/SNI 与真实主机名不一致，可能触发服务端白名单或证书校验失败，见 §7.4.6）；
- 生效：`podman stop devbox` + `podman start devbox`，然后容器内 `getent hosts mysql.corp.internal` 应返回 `10.129.12.75`；
- 回滚：删除标记段（含两行标记），再重启容器。

#### 7.4.5 排障判据：解析失败 / 解析到错 IP

分层定位，避免把解析问题误判成 DNAT 问题：

| 现象 | 判据（位置） | 结论 |
|---|---|---|
| `getent hosts <域名>` 为空 / `Name or service not known` | 容器内 | 解析失败，继续看下一行 |
| `/etc/resolv.conf` 的 nameserver 不是网关 | 容器内 | 该网络 `dns_enabled=false` 或用了 `--dns`：属另一条解析链路，本方案不覆盖 |
| 容器内失败、VM 内 `getent hosts <域名>` 成功 | VM | aardvark 转发/上游问题：查 `ss -lunp \| grep ':53'`（aardvark 是否在网关监听）与 VM `/etc/resolv.conf` |
| 容器内失败、VM 也失败 | VM / Windows | 上游 DNS 本身解析不了（aTrust DNS 未生效 / 缺 search 域）：Windows 侧 `Resolve-DnsName <域名>` 确认；必要时 §7.4.4 钉住 |
| 解析到**错误 IP**（公网/另一网段） | 容器内 `getent ahosts` | split-horizon：该域名在外部视角是公网地址 → §7.4.4 钉住为真实 IP；**不要**为错 IP 加 DNAT |
| 解析出 AAAA 且连接失败 | `getent ahosts` 有 v6 记录、Java 报 `Network is unreachable` | JDK 可能优先 AAAA（本方案只做 v4）→ 优先 §7.4.4 钉住（hosts 只有 v4 条目时 glibc 只返回 v4）；否则 `JAVA_TOOL_OPTIONS=-Djava.net.preferIPv4Stack=true` 兜底 |
| 解析正确但连接仍失败 | §6.1 0.3 的链计数器 | 问题不在解析：回到 DNAT / socat / portproxy 三段排查 |

取证（镜像无 `dig`/`tcpdump`，用最轻的方式直接问网关 DNS）：

```bash
# 容器内执行：发一个 A 查询给网关，看是否有应答
python3 - <<'PY'
import socket
name = 'mysql.corp.internal'
q = b'\x12\x34\x01\x00\x00\x01\x00\x00\x00\x00\x00\x00'
q += b''.join(bytes([len(p)]) + p.encode() for p in name.split('.')) + b'\x00\x00\x01\x00\x01'
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.settimeout(3)
s.sendto(q, ('10.89.0.1', 53))
try:
    data, _ = s.recvfrom(512)
    print('DNS-REPLY bytes=%d rcode=%d ancount=%d' % (len(data), data[3] & 0xF, (data[6] << 8) | data[7]))
except Exception as e:
    print('DNS-NO-REPLY', e)
PY
```

`rcode=0` 且有应答 → DNS 链路通，问题在"名字本身解析到哪"；`DNS-NO-REPLY` → 网关 53 不通（aardvark 未运行 / 网络未启用 DNS）。

#### 7.4.6 TLS/SNI 与证书

本方案只改报文目的 IP，不改写内容、不终止 TLS：客户端仍以**真实主机名**握手，SNI 与证书校验与直连一致。因此**不要**在 hosts 里把域名指向桥接地址（服务端看到的目标与证书不匹配，或触发基于 Host 的白名单）——这正是 §7.4.4 写"真实 IP"的原因。

### 7.5 VM 侧证据

```powershell
# 规则本体（纯 nft；真机形态）
podman machine ssh 'sudo nft list table ip cadence_dnat'
# 全量规则里定位本方案的自有表
podman machine ssh 'sudo nft list ruleset | grep -A6 -i cadence'
# conntrack：应有 <真实IP>:<端口> ↔ <服务表 bindaddr>:<vmPort> 的条目（通常 bindaddr=当前网关）
# 注：/proc/net/nf_conntrack 仅在 VM 内核带 CONFIG_NF_CONNTRACK_PROCFS 时存在；
#     无该文件时本项不作为判据，改用 nft 规则 + 容器内探针（§6.1-0.3）
podman machine ssh 'grep 10.129.12.75 /proc/net/nf_conntrack | head -3'
```

**重要**：不要用"VM 里直接 `curl/connect` 真实地址"做自测——那是 OUTPUT 路径，不经过 prerouting，会给出假阴性（真机已实测 `VM-DIRECT-FAIL`，§11.3-E1）。唯一的权威验证是 §6.1-0.3 的**容器内**探针（域名用例见 §6.1-0.4）。

## 8. 风险与边界

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **网段冲突**：某个真实地址恰好落在 podman 网桥子网内（或与容器自身地址重叠） | 容器会直接经网桥访问该地址，包到不了 VM 的 prerouting——改写规则永不命中 | **已实现**：生成端按 `podman network inspect` 的子网 CIDR 判定（`Test-InSubnet`），命中则**告警并跳过该条**（不阻断 relay 建链，与"附加能力只告警"一致）；落地前可另行 `ip route get <real_ip>` 复核 |
| R2 | **netavark/nftables 多表顺序**（E-DNAT 特有） | DNAT 不生效 | §6.1 门槛实测；先走 §6.2.2 的自建 nft table + 显式 `priority -101`（确定性顺序）；仍不通过再切 E-ALIAS（绕开 netfilter） |
| R3 | **网桥网关漂移**（podman 网络重建） | 真正失效的是 relay 本身：`cmd_setup` 在 bindaddr 不在本机网卡时直接 die（`relay-vm.sh:367-374`）、`cmd_status` 判 FAIL（`:583-587`）、socat 若重启则 `bind=<旧地址>` 起不来；DNAT 规则本身不是根因 | DNAT 目标固定取 relay 服务表 bindaddr（socat 实际监听处），保证"成功态下改写后有人接"，且规则内容不随运行时事实漂移（R-S2）；漂移**只告警**并提示重跑 `relay.ps1`（R20）；relay 自身的 hop3 仍按既有提示重跑 setup |
| R4 | **aTrust 重连后桥接地址变化** | 真实地址→vmPort 映射不变（relay.json 静态），但若远端地址本身变了需重建通道 | 用 `relay.ps1` 改址（已有交互流程）；映射表随 setup 重新生成 |
| R5 | **IPv6**：应用优先解析到 AAAA 时绕开本方案 | 连接失败或超时 | 文档标注仅 IPv4；域名场景用 `getent ahosts` 确认实际走向 |
| R6 | **容器重建/升级**：A 方案规则丢失 | 应用重新连不上 | E 无此问题；A 由 `relay.ps1` 重跑补回，README 写明 |
| R7 | **影响面**：E 作用于 `cadence_default` 上所有容器 | 其他容器访问同一真实地址也被重定向 | 这是期望行为；规则只匹配 `-d <real>/32 -p tcp --dport <port>`，不匹配其他流量 |
| R8 | **源 IP 语义**：真实服务看到的源是 Windows 宿主（relay 既有行为） | 若服务端依赖源 IP 白名单，需确认 | 现状已如此（socat→portproxy），本方案不改变；如遇问题反向排查白名单 |
| R9 | **UDP 不支持** | DNS 之外的 UDP 服务不可用 | 明确不在范围；如需扩，要给 relay 增加 UDP 能力（工作量另计） |
| R10 | **VM 重启后规则丢失**（手工阶段） | 恢复原故障 | 阶段 0 只是验证；阶段 1 用 systemd oneshot/boot 兜底保证持久 |
| R11 | **特权面**（A 方案）：`NET_ADMIN` 让容器内任何进程可改自身防火墙 | 安全边界略微收窄 | devbox 本就挂 `docker.sock`（等同宿主 root），边际影响小；仍作为不首选 A 的理由之一 |
| R12 | **`/etc/ld.so.preload` 自锁**（C 方案） | 容器无法 exec | 不采用 C；若将来采用，必须先在旁路容器验证 `.so` |
| R13 | **端口冲突**：E-ALIAS 要在 VM 上监听 `真实IP:真实端口`，若该地址端口已被占用（含误配的重复映射） | 监听起不来，客户端收到本地 RST | 生成端强制 `(real_ip, real_port)` 唯一；应用前 `ss -tlnp \| grep ':<port>'` 预检并显式报占用者；冲突时改用 E-DNAT（不新增监听，无此冲突） |
| R14 | **split-horizon**：公司域名在容器内解析到公网/错误 IP | DNAT 按 IP 匹配，**不会命中**，连接超时 | §6.1 的 0.2 判定；按 §7.4.4 在 VM `/etc/hosts` 钉住为真实 IP；**不要**为错 IP 加 DNAT |
| R15 | **AAAA 优先**：域名有 v6 记录，JDK 先试 v6（本方案只做 v4） | 报 `Network is unreachable`，但同一服务的 IP 用例正常 | §7.4.4 钉住（hosts 只有 v4 条目时 glibc 只返回 v4）；或 `JAVA_TOOL_OPTIONS=-Djava.net.preferIPv4Stack=true` |
| R16 | **VM `/etc/hosts` 可能被系统/云初始化重写**（WSL 默认每次启动重新生成） | 钉住的域名失效（回落到 DNS 原行为） | 不把它当持久文件：`cadence-relay-dnat.service` / boot 循环每次启动都调用 `hosts_apply` 重放标记段（R-S2）；`hosts_apply` 幂等可重入；标记段带自有前缀便于识别 |
| R17 | **域名条目变更后需重启容器才生效** | 改完立刻测仍旧失败，误判为"方案无效" | 文档与 `-Status` 输出明确提示；`hosts_apply` 后打印"需 `podman stop/start devbox`" |
| R18 | **旧域名残留**：服务改名/删域名后标记段未清理 | 容器里仍把旧名指向旧 IP | `hosts_apply` 每次全量重建标记段（先删后写），天然回收 |
| R19 | **VM 发行版被重置**：`podman machine rm`、`wsl --unregister` 或手工删除发行版 | `/etc/cadence-relay-dnat.env`、`cadence-relay-dnat.service`、`/etc/hosts` 标记段、以及内核对规则全部丢失；relay 的 socat 表同样丢失 | 恢复方式只有一条：**重跑 `relay.ps1`**（唯一入口，R-S1）；`-Status` 检测映射文件缺失即提示"重跑 setup"；正常 stop/start 与重启不触发此风险（见 R-S2 语义） |
| R20 | **gateway 漂移**：podman 网络重建后网关变化 | 若 DNAT 目标改成"运行时解析的新网关"，规则内容会随运行时事实改变（违背 R-S2），且成功态假设（"新网关有人监听"）不成立——socat 并没有绑到新地址；若写死旧值，同样只是失败方式不同 | DNAT 目标恒取 relay 服务表 `/etc/cadence-relay.env` 的 bindaddr、目标端口恒取其 vmPort（socat 实际监听处）；漂移判定以"bindaddr 是否仍在本机网卡"为主（`ip -o addr`，与 `cmd_setup:370`/`cmd_status:583` 同逻辑），`podman network inspect cadence_default --format '{{range .Subnets}}{{.Gateway}}{{end}}'` 仅作诊断增强；差异**只告警**并提示重跑 `relay.ps1`；服务表里查不到服务名 → 该条跳过并报错，绝不写空值/旧值；表内 `target_ip`/`target_port` 仅用于比对 |

### 11.2 术语

| 术语 | 说明 |
|---|---|
| 真实地址 | atrust 后真实内网 `IP:端口`，应用配置里写的那个 |
| 桥接地址 | VM 上 socat 监听、容器可达的 `<bindaddr>:<vmPort>`（通常等于网桥网关），如 `10.89.0.1:23306` |
| vmPort / hostPort | relay 端口推导值：`hostPort=远端+10000`、`vmPort=hostPort+10000` |
| DNAT | 目的地址转换；本方案在 VM 的 `nat/PREROUTING` 做无状态改写 |
| PREROUTING / OUTPUT | 报文进入与本机发出的两个 netfilter 钩子；前者对"到达 VM 的容器流量"生效 |
| 映射表 | 新增的 `relay-map.env`（5 段 + 可选第 6 段域名），与现有 4 段 socat 服务表并存 |
| aardvark-dns | podman 网络的权威 DNS：监听网关 `:53`，只对容器名/别名做权威应答，其余转发上游（F16/F17） |

#### 12.2.1 第 1 项：DNAT 目标取 bindaddr

- **bindaddr 就是 socat 的真实 bind 地址**：`relay.ps1:460` 写表头 `# name vmport bindaddr hostport`，`:461` 逐行写 `"<name> <vmPort> $gw <hostPort>"`；`relay-vm.sh:67` 按同序解析；生成的 run 脚本 `:139-141` 执行 `exec "$SOCAT" "TCP-LISTEN:$vmport,bind=$bindaddr,fork,reuseaddr" ...` → bindaddr 即 `bind=` 实参。
- **两表按服务名关联可靠**：`read_env:76`（服务名重复即 die）、`Collect-Services`（`relay.ps1:208-...`，用 `$names` 去重）都保证唯一；映射表 name 与 `$services` 同源。
- **awk 列号正确**：`$3`=bindaddr、`$2`=vmport，与 `relay.ps1:461` 的列序一致。
- **"真正失效的是 relay"成立**：`cmd_setup:367-374` 在 bindaddr 不在本机网卡时直接 die；`cmd_status:583-587` 对同一条件判 FAIL；socat 被 systemd 重启时 `bind=<旧地址>` 也不可能成功。
- **但"改指新网关更糟"不成立**：socat 已失效时，指旧 bindaddr（报文发往已非本机的地址→丢弃）与指新网关（到达新网关→无监听→RST）**都不通**，差别只是超时/拒绝。已把论证替换为三条硬性质：成功态恒有人接、规则内容不随运行时事实漂移（R-S2）、失败可定位。
- **自洽性缺口（v1.1 存在，已修）**：§6.2 步骤 3 重启判据、§6.2 步骤 4 必做验收、§7.5 conntrack 三处仍写"当前 gateway"；§5.3 规则 3 只比对 `target_ip`、未比对 `target_port`。
- **新增判断**：漂移主判据改为 `ip -o addr`（复用 `:370`/`:583` 既有逻辑），`podman network inspect` 降为诊断增强——原设计"读不到就跳过"会让漂移在 VM 内 CLI 不可用时**永不告警**（§11.4-7）。

#### 12.2.2 第 2 项：`ExecStart` 走 `/bin/bash`

- **必须带解释器**：`relay.ps1:481`/`:542`/`:579` 一律以 `sudo bash /usr/local/bin/relay-vm.sh ...` 调用，`mv`（`:476-478`）不做 `chmod`；仓库唯一被 unit 直接执行的是 `write_run_script` 生成的 `$RUN_SCRIPT`，它在 `relay-vm.sh:143` 显式 `chmod +x`。⇒ 直接 exec `relay-vm.sh` 有失败风险，`/bin/bash` 前缀正确。
- **开机自动重放成立**：`[Install] WantedBy=multi-user.target` + `enable`，与既有每服务单元 `:511-527` 同一机制。
- **`Type=oneshot` + `Restart=on-failure` 合法**：`systemd.service(5)` 只禁止 oneshot 配 `Restart=always`/`on-success`（原文 "For Type=oneshot, Restart=always and Restart=on-success are not allowed"），`on-failure` 自 v244 起允许，与 `RemainAfterExit=yes` 组合即官方 "stoppable oneshot"。**但 v1.1 给的理由（兜 gateway 未就绪）在修正 #1 后不成立**——gateway 读取已非致命；已改为"兜 iptables 未就绪/映射表短暂缺失"，并标注 systemd ≥244 前提（§11.4-8）。
- **`ExecStop=dnat-flush` 不会造成"清了不再建"**：flush 只在 stop/关机执行，单元仍 enabled，下次 start/开机由 `ExecStart` 重建；语义即"stop 即失效"。
- **v1.1 未讲全的三件事（已补到 §6.2 步骤 3）**：① 单元由 `relay-vm.sh` 在 `cmd_setup` ④ 段（`:437-470`）写出，须登记 `SNAP_FILES`/`NEW_FILES`，`SNAP_ENABLED`/`SNAP_ACTIVE` 须纳入 `cadence-relay-dnat`；② ⑥ 段（`:511-527`）`enable --now`，新 enable 记入 `NEW_ENABLED` 供 `rollback_setup` 撤销；③ `cmd_teardown` 的 rm 清单（`:633`）必须加单元、dnat env、nft 标记文件，并先 `disable --now`。

#### 12.2.3 第 3 项：`Test-HostName` 拒绝 IP 字面量

- **必要且与 §5.3 第 5 条一致**：`^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?$` 会放行 `10.129.12.75`，故必须前置 IP 字面量拒绝。
- **不充分的拒绝面（已补）**：空串、含空白、`.`/`-` 首尾、连续点、总长 >253、单标签 >63；大写建议 `ToLowerInvariant()` 归一化（幂等）。
- **清空语义缺失（重要）**：按"回车=保持原值 + `Test-HostName` 不接受 `-`"，用户**永远无法删除**已录入域名。v1.2 引入输入侧 `-`/`none` = 清空；映射表第 6 列的 `-` 仍是占位符，两者语义分离。
- **闭合性（原文档最大缺口）**：`Test-AddrFormat` 校验的是整串 `IP:端口`（`relay.ps1:165`，调用点 `:171`/`:184`）。输入变成 `IP:端口[ 域名]` 后，**任何直接把 `$val` 交给 `New-Service*` 的路径都会因空格失败**。v1.1 只给 `Split-AddrInput` 代码、没点名调用点；v1.2 已逐个点名：`:298-307`（修改项）、`:320-323`（`-MySQL`/`-Redis`：保持纯 IP，但覆盖同名服务时须保留旧 host）、`:350-353`（自定义新增）、`:361-364`（目录新增）；并点名 `Collect-Services:215-220` 的旧对象重建必须带 `host`。
