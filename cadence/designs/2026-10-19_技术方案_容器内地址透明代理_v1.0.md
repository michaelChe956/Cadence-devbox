## 0. 结论摘要

> **决策状态（2026-10-19 用户拍板）**：Q1 = **允许改 WSL VM 侧 relay**，走主方案 E-DNAT；Q3 = `relay.json` 已含全部真实地址；Q5 = 配置里**存在域名**，非全 IP（域名专章见 §7.4）。Q2（给容器加 `NET_ADMIN` 并重建镜像）按默认**不做**，A 方案仅作退路记录。

1. **主方案：VM 侧 DNAT（方案 E-DNAT）**——在 WSL 的 podman machine 里用一条 `nat`/`PREROUTING` DNAT，把 `<真实地址>:<端口>` 无状态改写成 `<网桥网关>:<vmPort>`。容器零特权、零镜像改动、零工程配置改动、容器重建后仍生效；复用已有 relay 子系统（root 通道、systemd 自恢复、事务式回滚均已存在）。
2. **域名场景的最终形态**：容器内解析链固定为「容器 `/etc/resolv.conf`（只指向网关）→ 网关 `:53` 的 aardvark-dns → 上游（VM `resolv.conf` → Windows/aTrust DNS）」。**只要解析结果是真实 IP，DNAT 自动接管，零额外配置**；解析失败、解析到错 IP（split-horizon）、或存在 AAAA 优先时，由 relay 子系统在 **VM 的 `/etc/hosts`** 里用标记段把 `域名 → 真实IP` 钉住（容器重启时 podman 以 VM `/etc/hosts` 为基底生成容器内 `/etc/hosts`，因此零容器改动）。映射表新增**可选第 6 列**记录域名，仅用于诊断核对，不参与规则生成。
3. **同层备选：VM 侧地址别名 + socat（E-ALIAS）**——若实测 DNAT 未被命中（netavark/nftables 多表顺序等），改用「VM 把真实地址挂到 lo + socat 监听真实地址」，绕开 netfilter。
4. **容器侧备选 A（`NET_ADMIN` + `iptables -t nat OUTPUT` DNAT）**——因 Q1 已确认走 VM 侧，**不采用**；仅作为"VM 侧被策略锁死"时的退路记录（代价：改 `compose.yaml`、重建镜像、已有安装目录 compose 不会被 `install.ps1` 覆盖）。
5. **明确不选**：B（与 A 同权限但多进程多依赖）、C（LD_PRELOAD，全容器进程风险 + 需外部编译）、D（应用层覆盖，不满足"透明"）、F（redsocks/tun2socks/gost 无额外收益）。
6. **今天即可验证**：Windows 侧命令（§6.1），含一条**域名用例**，不需要任何代码改动。

## 1. 问题与目标

### 1.1 现象与链路

Spring 工程从 ibos-config-server 拉到的是 atrust 后的真实内网地址（例：`10.129.12.75:3306`）。容器内直连该地址失败，因为：

- 容器发包 → podman 网桥（`cadence_default`，网关例 `10.89.0.1`）→ WSL VM 转发 → Windows 侧 VPN；
- VPN（aTrust）**丢弃一切 NAT 转发流量**（`devbox/README.md` §2.6 "实测定论"）；
- 而容器可直接访问的，是 VM 上 socat 监听的桥接地址（例 `10.89.0.1:23306`），它经 `127.0.0.1:13306` → Windows portproxy → VPN，属于宿主发起流量，VPN 放行。

因此缺的只有一件事：**把"进程要去的真实地址"在报文层替换成"VM 上已存在的桥接地址"**。

### 1.2 "透明"的定义（本设计的硬判据）

对容器内**任意进程**（含 JVM、`podman exec` 起的 shell、构建工具、AI CLI 自身）：

| # | 要求 |
|---|---|
| T1 | 进程仍然写/用真实地址，不做任何地址换算；应用代码、启动参数、环境变量均不需要知道桥接地址 |
| T2 | 不改配置中心里的数据（只读，不写） |
| T3 | 不改工程配置文件（`application.yml`/`bootstrap.yml`/`pom.xml` 等一律不动） |
| T4 | 不改容器启动参数与镜像（主方案必须满足；备选方案允许，但要显式列出代价） |
| T5 | 容器重建、镜像升级、VM/宿主重启后无需人工干预即恢复 |

### 1.3 成功判据（可观测）

| # | 判据 | 验证命令 |
|---|---|---|
| S1 | 容器内 `bash` 直连 `<真实IP>:<端口>` 成功（TCP 建连） | §7.1 |
| S2 | 容器内 **JVM** 直连真实地址成功（排除"只有 shell 能连"的假阳性） | §7.2 |
| S3 | Spring 工程启动到就绪，数据源/Redis/ZK 初始化无 `Connection timed out`/`Connection refused` | §7.3 |
| S4 | 容器内本地 stack 中间件（`127.0.0.1:3306`、`127.0.0.1:6379`）行为不变 | §7.6 |
| S5 | 映射之外的真实地址、以及外网访问，行为不变（无全量劫持） | §7.6 |
| S6 | 回滚后恢复原状：直连真实地址重新失败，其余一切不变 | §6.5 |
| S7 | **域名用例**：容器内以域名连接成功，且 `getent hosts <域名>` 与 `relay.json` 的真实 IP 一致（Q5） | §6.1-0.4、§7.4.1 |

### 1.4 范围

**包含**：TCP 服务（MySQL/Redis/ZooKeeper/配置中心/Kafka broker 等）；IPv4；单台 devbox 容器及其所在 `cadence_default` 网络；**域名场景**的解析判定与"域名 → 真实 IP"固定（§7.4）。

**不包含**：UDP 服务的代理（现有 relay 只有 `socat TCP-LISTEN`，无 UDP 能力，映射表也按 TCP 设计）；**面向 IPv6 目标地址**的代理（DNAT 只做 v4；域名带 AAAA 时的处理见 §7.4.5）；域名解析服务本身的重建（不自建 DNS，理由见 §7.4.3）；多宿主/多网桥拓扑；aTrust 侧配置。

## 3. 环境判定（落地前必须先跑）

### 3.1 容器内一条命令（只读探测，不改任何东西）

在目标机器的 devbox 容器里执行（`podman exec -it devbox bash` 后整段粘贴）：

```bash
set -u
echo "== 身份/权限 =="
id
sudo -n true 2>/dev/null && echo "sudo=OK" || echo "sudo=NO"
awk '/^Cap(Inh|Prm|Eff|Bnd):/{print}' /proc/self/status
cap=$(sudo grep '^CapBnd:' /proc/self/status | awk '{print $2}')
echo "NET_ADMIN(in CapBnd)=$(( (16#${cap:-0} >> 12) & 1 ))"

echo "== 工具 =="
for b in iptables iptables-legacy nft ip ss socat python3; do
  printf '%-14s %s\n' "$b" "$(command -v "$b" 2>/dev/null || echo ABSENT)"
done

echo "== netfilter 可用性 =="
sudo iptables -t nat -L -n >/dev/null 2>&1 && echo "nat-table=OK" || echo "nat-table=FAIL"
nft list ruleset >/dev/null 2>&1 && echo "nft=OK" || echo "nft=FAIL"

echo "== 加地址是否被允许 =="
sudo ip addr add 127.0.0.2/32 dev lo 2>&1 | head -1
sudo ip addr del 127.0.0.2/32 dev lo 2>/dev/null

echo "== 现实连通性 =="
timeout 3 bash -c 'echo > /dev/tcp/10.129.12.75/3306' 2>/dev/null \
  && echo "real-addr=REACHABLE" || echo "real-addr=UNREACHABLE"
gw=$(awk '$2=="00000000"{print $3; exit}' /proc/net/route); gw=${gw:-00000000}
printf 'default-gw=%d.%d.%d.%d\n' \
  "$((16#${gw:6:2}))" "$((16#${gw:4:2}))" "$((16#${gw:2:2}))" "$((16#${gw:0:2}))"
```

把 `10.129.12.75/3306` 换成用户当前报错的那个地址即可。

### 3.2 判定矩阵（按输出选路径）

| 观测 | 结论 |
|---|---|
| `NET_ADMIN(in CapBnd)=0`（预期） | 容器侧 A/B **不可行**（即使 `sudo` 成 root 也不行，cap 在容器配置里被裁剪）→ 走 **E**（主方案） |
| `NET_ADMIN=1` 但 `iptables`/`ip` 为 `ABSENT` | A/B 需先加包（镜像改 `Dockerfile` 或运行时 `apt-get`）；仍要改 compose → 只作备选 |
| `NET_ADMIN=1` 且 `nat-table=OK` | A 可行；但仍需改 compose + 镜像 → 见 §4.1 代价 |
| `nft=FAIL` / `nat-table=FAIL` 且报错含 `can't initialize iptables table` | 内核 netfilter 模块缺失 → 容器侧直接排除；VM 侧也要在 §3.3 查 |
| `real-addr=REACHABLE` | 不需要代理——先查应用的真实失败原因（端口/白名单/账号），不要继续本方案 |
| `default-gw=` 不是 `10.89.0.1` | 网桥网关已漂移：`relay.ps1 -Status` 会报 hop3，先重跑 relay setup 再谈映射 |

### 3.3 Windows / VM 侧自检（E 方案的前置）

```powershell
# 1) VM 是否运行、root 是否可用
podman machine ssh 'id -u'
# 2) VM 是否有 netfilter 工具与表
podman machine ssh 'iptables --version; nft list tables 2>/dev/null | head; iptables -t nat -S PREROUTING | head -12'
# 3) 当前网桥与网关（映射表 target 的依据）
podman network inspect cadence_default --format '{{range .Subnets}}{{.Subnet}} gw={{.Gateway}}{{end}}'
# 4) relay 是否已在跑（应有 cadence-relay@mysql 等）
podman machine ssh 'systemctl list-units "cadence-relay*" --no-pager'
```

判读：

- `iptables --version` 含 `nf_tables` → 规则进 `ip` 表，可被 `nft list ruleset` 看到；含 `legacy` → 只进 xtables。**两种都能用**，但 §7.5 的核对命令要对应。
- `iptables -t nat -S PREROUTING` 里会看到 netavark 的跳转链（发布端口 DNAT）。**不要**改它们，只新增自己的链（§6.1）。

### 3.4 三类失败要分开读

| 报错 | 含义 | 处理 |
|---|---|---|
| `Permission denied (you must be root)` / `Operation not permitted` | 缺 `NET_ADMIN` | 走 E；或按 §4.1 加 cap |
| `can't initialize iptables table 'nat'` | 内核模块缺失（容器通常 `ls /lib/modules` 为空，靠宿主内核） | 容器侧排除；VM 侧通常可用（podman 自身依赖 NAT） |
| `iptables: command not found` | 只是没装二进制 | 与权限无关，别误判为"无权限" |

## 4. 方案对比

### 4.0 总表

**能力维度**

| 方案 | 落点 | 透明度 | 所需权限 | 需重启容器 | TCP / UDP | 容器重建后存活 |
|---|---|---|---|---|---|---|
| A 容器 DNAT（`nat OUTPUT`） | 容器 netns | 全进程 | `NET_ADMIN` + root | 是 | TCP；UDP 可同规则 | 否（需再应用） |
| B 容器 lo 别名 + socat | 容器 netns | 全进程 | `NET_ADMIN` + root | 是 | TCP；UDP 需换转发器 | 否 |
| C LD_PRELOAD `connect()` | 进程地址空间 | 仅动态链接进程（Go/Bun/静态二进制绕过） | 无（写 `/etc/ld.so.preload` 则需 root） | 否（仅新进程） | TCP/UDP 的 `connect` 均可见 | 需镜像/卷持久 |
| D 应用层覆盖 | 应用参数/环境 | **否**（逐应用、逐键） | 无 | 是 | 取决于应用 | 是（改启动命令） |
| E-DNAT（**推荐**） | VM root netns | 全容器全进程 | VM root（已有） | 否 | TCP（可扩 UDP） | 是 |
| E-ALIAS | VM root netns | 全容器全进程 | VM root（已有） | 否 | TCP | 是 |
| F redsocks/tun2socks/gost | 容器 netns | 全进程 | `NET_ADMIN`/`privileged` + `/dev/net/tun` | 是 | 取决于实现 | 否 |

**成本维度**

| 方案 | 额外依赖 | 故障影响面 | 可维护性（归属） | 实施体量 |
|---|---|---|---|---|
| A | 镜像加 `iptables`+`iproute2`；compose 加 `cap_add` | 仅 devbox 容器 | 中：3~4 个文件（Dockerfile/compose/relay.ps1/README） | 中 |
| B | 同上 + `socat`或自研转发器 + 监督循环（容器无 systemd，`init:true` 只做回收） | 仅 devbox 容器 | 低：要自己写守护 | 大 |
| C | 外部编译 `.so`；供应链 | **全容器进程**（坏 `.so` 会让 `podman exec` 都起不来） | 低 | 大 |
| D | 无 | 单应用 | 极低（键多、优先级不确定） | 小但重复劳动 |
| E-DNAT | VM 已有 `iptables` | `cadence_default` 上所有容器（符合预期） | 高：并入 relay 子系统，沿用事务/自恢复 | 中（+1 映射文件 +2 子命令） |
| E-ALIAS | VM 已有 `ip`/`socat` | 同上 | 高 | 中 |
| F | 额外软件 + TUN | devbox 容器 | 低 | 大 |

### 4.1 A：容器 `NET_ADMIN` + `iptables/nft` OUTPUT DNAT

前置（三项都满足才成立）：

1. `compose.yaml` 的 `devbox` 加 `cap_add: [NET_ADMIN]`（或 `--cap-add=NET_ADMIN`，走 `podman run` 路线时）；
2. 镜像里加 `iptables`、`iproute2`（`devbox/Dockerfile:27-30` 的 apt 清单），需重建 + 重新分发镜像；
3. 容器能读到映射表（`/cadence/stack/data/relay-map.env`，见 §5）。

规则形态（幂等）：

```bash
sudo iptables -w 5 -t nat -N CADENCE-DNAT 2>/dev/null || true
sudo iptables -w 5 -t nat -C OUTPUT -j CADENCE-DNAT 2>/dev/null || \
  sudo iptables -w 5 -t nat -I OUTPUT 1 -j CADENCE-DNAT
sudo iptables -w 5 -t nat -F CADENCE-DNAT
while read -r name real_ip real_port target_ip target_port; do
  target_port=${target_port%$'\r'}
  case "$name" in ''|'#'*) continue ;; esac
  sudo iptables -w 5 -t nat -A CADENCE-DNAT -d "$real_ip/32" -p tcp --dport "$real_port" \
    -j DNAT --to-destination "$target_ip:$target_port"
done < /cadence/stack/data/relay-map.env
sudo iptables -w 5 -t nat -L CADENCE-DNAT -n -v
```

代价与坑：

- **已有安装不会被自动修好**：`install.ps1` 不覆盖已存在的 `stack/compose.yaml`（F14），用户必须手工加 `cap_add` 或按文档迁移；
- `nat OUTPUT` 上的 DNAT 依赖 conntrack 反向改写，历史上对本地生成流量有过若干边界问题——**必须**用 §7.2 的 JVM 探针实测，不能只用 shell 的 `/dev/tcp` 下结论；
- 容器 netns 若被重建（`podman rm/run`），规则全丢，需要重新应用；
- 权限面扩大：容器内任何进程都能改自己 netns 的防火墙（对已挂 `docker.sock` 的 devbox 属于边际增加，但不是零）。

### 4.2 B：容器 `NET_ADMIN` + lo 别名 IP + socat/REDIRECT

机制：`ip addr add <真实IP>/32 dev lo`，使 `connect(<真实IP>:<端口>)` 落到本地；再由监听该地址的转发器送到 `10.89.0.1:<vmPort>`。

**不选 B（作为主方案）的理由**：

- 与 A **同样的权限要求**（都要 `NET_ADMIN`），但还要额外的 `iproute2` + 转发器 + **自己写监督循环**（容器里没有 systemd，`init: true` 只回收僵尸进程）；
- 多一层进程，故障面更大（转发器挂了 → 表现为"连接被拒"，比"规则丢失"更难辨）；
- 同样的机制放到 VM 侧就变成 E-ALIAS，直接白拿 systemd `Restart=always`——没有理由在容器里重造。

### 4.3 C：无特权 `LD_PRELOAD` 改写 `connect()`

机制：编译一个 `.so` 拦截 `connect(2)`，命中映射表时改写 `sockaddr_in`；用 `/etc/ld.so.preload`（全容器）或 `LD_PRELOAD`（逐进程）加载。

**Java 下可行性**：Temurin 21 是动态链接 glibc，`java.net` 的 `NET_Connect` 最终调用 libc `connect`；`SocketChannel`、Netty 的 epoll 原生传输同样落到 libc `connect`。所以**对 JVM 是有效的**——这也是它值得评估的原因。

**坑（逐条都会咬人）**：

1. **不是全进程**：Go、Bun/Zig 等直接走系统调用，静态链接二进制完全绕过——写"全进程透明"就是错的；
2. 需要**外部编译**（镜像无 `gcc`），引入一条二进制供应链；
3. `/etc/ld.so.preload` 里放坏 `.so` → **整容器不可 exec**，只能 `podman cp` 修文件或重建容器；恢复成本极高；
4. `sudo` 的 secure-exec 会剥离 `LD_PRELOAD`（`/etc/ld.so.preload` 不受影响，但风险如 3）；
5. 只覆盖 `connect`：`getaddrinfo`（域名）、IPv6、UDP 的 `sendto` 无地址参数等都要单独处理；
6. 只对**新启动**的进程生效，已在跑的 JVM 无感知。

结论：仅当"无 VM 权限 + 不改容器参数"同时成立时才考虑；本场景 VM 权限已经存在（relay 就是这样工作的），没有必要承担 3 的风险。

### 4.4 D：应用层覆盖（Spring Cloud Config / 启动参数 / 环境变量）

机制：给每个应用加 `--spring.datasource.url=...`、`SPRING_REDIS_HOST=...` 等。

**不满足"透明"的理由**：

- 需要**逐应用、逐键**列举（数据源 URL、Redis host/port、ZK `connectString`，以及项目自定义键），键名要先从配置中心或工程里挖出来——这是"改工程配置"的变体；
- 优先级不确定：Spring Boot 命令行参数最高，但 **Spring Cloud Config 客户端默认 `override-system-properties=true`**，`-D`/系统属性可能被远端配置反覆盖；环境变量是否生效还取决于 `spring.cloud.config.override-*` 开关——**必须逐项目实测**（本设计未实测，标注为假设）；
- 多应用、多环境、多版本并存时维护成本线性增长，且新人不知道要加。

结论：只作为单项目应急（在启动命令上显式给 `--spring.datasource.url=jdbc:mysql://10.89.0.1:23306/...`），不作为通用方案。

### 4.5 E：VM 侧方案（推荐）

#### 4.5.1 E-DNAT（主方案）

**为什么成立**：容器到 `10.129.12.75` 的包本来就要经过 VM（默认路由指向 `10.89.0.1`）。在 VM 的 `nat`/`PREROUTING` 里把它 DNAT 成 `10.89.0.1:23306`（VM 本地地址）后：

```text
容器进程 connect(10.129.12.75:3306)
  → veth/网桥 → VM PREROUTING 命中 DNAT → 目标改为 10.89.0.1:23306（VM 本地）
  → 已有 cadence-relay@mysql 的 socat 接住 → 127.0.0.1:13306
  → Windows portproxy → VPN → 真实 MySQL
返回按 conntrack 反改写，客户端看到的对端仍是 10.129.12.75:3306。
```

- **零容器特权**：VM 里本来就是 root（F2）；
- **零镜像/零 compose/零工程配置改动**；
- **容器重建、升级镜像都不影响**（规则在 VM 根 netns）；
- **复用已有自恢复**：套用 `cadence-relay@*` 的 systemd/boot 兜底模式（F3）；
- 覆盖 `cadence_default` 上**所有**容器（对"任意进程"是加分，不是负担）。

**必须实测的门槛（放在写代码之前）**：现代 podman + netavark 通常用 nftables 建表（具体后端以 §3.3 `iptables --version` / `nft list tables` 实测为准），而本方案在 `ip nat` 表里另建一条 base chain。同为 `dstnat` 优先级、不同表时的遍历顺序**不是强保证项**——必须先在目标机用 §6.1 的手工命令验证包确实被改写（看链计数器与 `conntrack`），再进入产品化。不通过就切 E-ALIAS。

另一处实现选择：跳转规则默认**不限 `-i`**（只按 `-d <real>/32 -p tcp --dport <port>` 匹配），这样从镜像网卡转发进来的同类流量也会被改写，语义一致；若确认网桥接口名稳定（`podman network inspect` 可取），可加 `-i <网桥接口>` 收窄，属于可选加固。

**已知边界**：只对"到达 VM 的报文"生效；VM 自己 `connect(真实IP)` 走 OUTPUT，不经过这条 PREROUTING（所以 §7.5 的 VM 侧自测方式要写对，别用宿主直连做假阴性判断）。

#### 4.5.2 E-ALIAS（同层备选）

机制：VM 里 `ip addr add <真实IP>/32 dev lo`，让该地址成为**本地地址**；再为每个映射起一个 socat：`TCP-LISTEN:<真实端口>,bind=<真实IP>,fork,reuseaddr TCP:10.89.0.1:<vmPort>`。

- 完全绕开 netfilter：不存在多表顺序、conntrack、NAT 后端差异问题；
- 可直接 `ss -tlnp` 看到监听、`netstat -antp` 看到连接，排查直观；
- 代价：每个映射一个进程（沿用 `cadence-relay@` 的 systemd/boot 模式，成本已知）；地址别名要按真实 IP 维护；
- 触发条件：E-DNAT 门槛不通过；或 VM 内核/nftables 被策略锁定。

### 4.6 F：其他（不展开，仅说明为何不选）

| 候选 | 结论 |
|---|---|
| redsocks / tun2socks | 都需要 `NET_ADMIN`（redsocks 靠 iptables 重定向；tun2socks 要 `/dev/net/tun`），容器侧权限条件与 A/B 相同，却多一个常驻进程与配置面 |
| gost | `-L redirect://`/TProxy 同样依赖 iptables；作为普通端口转发器（`-L tcp://:23306`）不解决"客户端仍连真实地址"的问题 |
| `unshare -Urn` 无特权 netns | 需要内核允许非特权 user namespace + `slirp4netns`/`pasta`（镜像未装），且新 netns 看不到容器本地 stack 中间件；改造面远大于收益 |
| 共享 devbox netns 的 sidecar 加 `NET_ADMIN` | 依赖 podman-compose 对 `network_mode: service:...` 的支持（未验证），且 sidecar 仍要装 `iptables`；不如直接把规则放 VM |
| `/etc/hosts` 改写 | 只能覆盖**域名**，配置里是 IP 时无效；仅作为 §7.4 的域名补充手段 |

### 4.7 推荐与触发条件

| 选择 | 触发条件 | 当前状态（2026-10-19） |
|---|---|---|
| **E-DNAT（主）** | 默认路径；§6.1-0.3 手工验证通过 | **已选定**（Q1 允许改 VM 侧） |
| E-ALIAS | E-DNAT 门槛不通过（计数器不增长 / conntrack 无记录 / 包仍被转发出去） | 待阶段 0 判读后决定 |
| A（容器侧） | 仅当 VM 侧被策略锁死、且用户改判允许改容器 | **已否决**（Q2：不加 `NET_ADMIN`、不重建镜像） |

| D | 单个项目的临时应急 | 不进入本方案 |
| B / F | — | 不选 |

## 5. 映射表设计

### 5.1 数据从哪来

| 来源 | 用法 | 说明 |
|---|---|---|
| **`relay.json`（权威）** | 生成映射表的唯一输入 | 已含每个服务的 `remote`（真实 `IP:端口`）、`vmPort`、`gateway`（F4）。用户在 `relay.ps1` 里配 relay 时已经录过一遍，不重复劳动 |
| 配置中心只读查询 | 补齐未入 relay 的地址 | `curl -s "http://<config-server>:<port>/<应用名>/<profile>"`（Spring Cloud Config 端点）后用正则提取 `IP:端口` |
| 运行中应用 | 同上 | `curl -s http://127.0.0.1:<port>/actuator/env`（若开了 actuator） |
| 启动失败日志 | 最可靠的"缺了哪个" | 超时/拒绝日志里的 `host:port` |
| 工作区扫描 | 辅助发现 | 见下方命令；注意**配置中心的真实值可能不在工作区里**，扫描结果只能当线索 |
| 用户直接提供 | 兜底 | 有疑义以用户为准 |

Q3 已确认 `relay.json` 已含全部真实地址：下表其余来源只用于**发现遗漏**与异常排查，**不作为**映射表的生成输入。

发现用一次性命令（只读）：

```bash
# 工作区里的 IP:端口 线索（按出现次数排序）
grep -rhoE '([0-9]{1,3}\.){3}[0-9]{1,3}:[0-9]{2,5}' /workspace \
  --include='*.yml' --include='*.yaml' --include='*.properties' --include='*.xml' 2>/dev/null \
  | sort | uniq -c | sort -rn | head -30
```

补齐流程：发现一个未映射的 `真实IP:端口` → 用 `relay.ps1` 新增一个服务（目录项或 `custom`，服务名限 `[A-Za-z0-9_-]`）→ 重跑 setup → 映射表自动带上。**不要**手工只改映射表而不建 relay 监听：那样 DNAT 的目标端口根本没人监听。

### 5.2 为什么必须新开文件（不能扩展现有的 4 列表）

`relay-vm.sh` 在 4 处按**恰好 4 段**解析（F1）：

```bash
while read -r name vmport bindaddr hostport; do
```

第 5 段会被 `hostport` 吃掉（变成 `"13306 额外内容"`），随后 socat 目标变成 `TCP:127.0.0.1:13306 额外内容`，身份核验 `is_expected_socat` 全部失配，systemd 拉起也会报错。改格式等于同时改 4 个解析点 + 所有测试桩的 argv 断言（F15），不划算。

因此：**现有表原样不动，新增第二个文件**。

### 5.3 映射文件格式与校验

两个位置、同一内容（一份给容器侧方案用，一份给 VM 用）：

| 位置 | 容器/VM 可见路径 | 用途 |
|---|---|---|
| `<安装目录>/stack/data/relay-map.env` | `/cadence/stack/data/relay-map.env` | A/B/C 在容器内读取 |
| VM `/etc/cadence-relay-dnat.env` | — | E 在 VM 内读取 |

选 `stack/data/` 的理由：`/cadence/stack` 是 bind mount（F13），`data/` 已在安装器 `.gitignore` 里，且不在 entrypoint 步骤 4 的模板同步清单内（F12）——不会被覆盖、不污染仓库。

格式（**5 段必填 + 第 6 段可选域名**，空白分隔，`#` 注释，CRLF 容忍）：

```text
# 由 relay.ps1 生成，勿手改。
# <name> <real_ip> <real_port> <target_ip> <target_port> [domain]
mysql 10.129.12.75 3306 10.89.0.1 23306 mysql.corp.internal
redis 10.129.20.31 6379 10.89.0.1 26379
zk1   10.129.30.11 2181 10.89.0.1 22181 zk1.corp.internal
```

第 6 段（`domain`）的定位：**只用于诊断与文档**（`-Status` 用它核对"容器内解析结果是否等于 `real_ip`"），**不参与规则生成**——DNAT 只匹配 IP，域名路径见 §7.4.2。可以省略，也可写 `-` 表示"该服务在配置里只用 IP"。

为什么不是"第 6 列换成域名、由消费端自己解析"：
- 解析结果取决于**容器视角**，而消费端（VM 侧脚本）解析出来的是 VM 视角，两者可能不一致（split-horizon）——用 VM 的解析结果去反推容器行为，正是要避免的错误来源；
- 真实地址必须由人确认、可审计（Q3 已确认 `relay.json` 含全部真实地址），不能让脚本"猜"。

校验规则（生成端与消费端**都要**做，任一条不满足直接报错，不静默跳过）：

1. `name` 匹配 `^[A-Za-z0-9_-]+$`；`real_ip`/`target_ip` 是合法 IPv4 点分十进制；端口 `1..65535`；
2. `(real_ip, real_port)` 唯一（同一真实地址端口不能有两个目标）；
3. `target_ip` 必须等于当前网桥网关（消费侧比对，漂移即报"重跑 setup"）；
4. 行尾 `\r` 剥离（沿用 `read_env` 的 `${var%$'\r'}` 风格）；
5. 第 6 段若存在：匹配 `^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?$` 或等于 `-`；**不得**是 IP 字面量（域名段写 IP 视为配置错误，提示改用 `real_ip` 段）。

### 5.4 生成与分发（幂等）

在 `relay.ps1` 的 `Invoke-Setup` 里，`relay.json` 落盘成功后追加一步。`relay.json` 的 `services[]` 增加**可选**字段 `host`（域名，可为空；`remote` 仍是 `IPv4:端口`，不动 `Test-AddrFormat`，F19——加字段是 JSON 层面的纯增量，不影响既有交互问答与端口推导）：

```powershell
# 由 services[] + gateway 生成；顺序 = relay.json 顺序（确定性）
$mapLines = foreach ($s in $cfg.services) {
  $h, $p = $s.remote -split ':', 2
  $dom = if ($s.PSObject.Properties.Name -contains 'host' -and $s.host) { $s.host } else { '-' }
  '{0} {1} {2} {3} {4} {5}' -f $s.name, $h, $p, $cfg.gateway, $s.vmPort, $dom
}
$map = "# 由 relay.ps1 生成，勿手改。`n# <name> <real_ip> <real_port> <target_ip> <target_port> [domain]`n" `
     + (($mapLines -join "`n") + "`n")
$mapFile = Join-Path (Join-Path $InstallDir 'stack') 'data\relay-map.env'
New-Item -ItemType Directory -Force (Split-Path $mapFile) | Out-Null
Set-Content -Encoding ascii -NoNewline $mapFile $map       # ascii：无 BOM，bash 侧零坑
podman machine cp $mapFile "${mach}:/tmp/cadence-relay-dnat.env"
$null = podman machine ssh 'sudo mv /tmp/cadence-relay-dnat.env /etc/cadence-relay-dnat.env'
```

同时，**只为需要钉住的域名**生成一段 `/etc/hosts` 片段（写入位置与生效方式见 §7.4.4；此处只描述产物）：

```powershell
$hostLines = foreach ($s in $cfg.services) {
  if (-not ($s.PSObject.Properties.Name -contains 'host') -or -not $s.host) { continue }
  $ip, $p = $s.remote -split ':', 2
  '{0} {1}   # cadence-relay:{2}' -f $s.host, $ip, $s.name   # 域名 → 真实 IP
}
# 仅当 §6.1-0.2 判定"该域名在容器内解析不到真实 IP / 解析到错 IP"时才下发；否则不要写
```

要点：

- **必须无 BOM**：`Set-Content -Encoding utf8`（WinPS 5.1）会写 BOM，首行的 `name` 会变成 `\ufeffmysql`，bash 侧校验直接失败。沿用仓库已有做法 `-Encoding ascii`（`relay.ps1:469` 写服务表就是这个写法）；
- **原子写**：先写 `.tmp` 再 `Move-Item -Force`，避免半截文件被消费；
- **幂等**：同一份 `relay.json` 重跑生成字节级一致；不追加、不去重表；
- **`host` 不参与规则生成**：DNAT 只按 `real_ip`/`real_port` 匹配；域名路径靠解析（§7.4.2），`host` 只供 `-Status` 核对解析结果；
- **失败语义**：映射文件写失败 → 按现有 `Invoke-Setup` 的失败路径处理（`Undo-Portproxy` + `Die`），因为此时 DNAT 目标也不该存在。

### 5.5 数据流与落点（四份文件的关系）

```text
relay.ps1 问答/参数
   └─ relay.json（安装目录根；权威：真实地址 + 端口推导 + gateway + 可选 host）
        ├─ <安装目录>/stack/data/relay-map.env ──bind mount──> 容器 /cadence/stack/data/relay-map.env
        ├─ podman machine cp ──> VM /etc/cadence-relay-dnat.env
        │                          ├─ 与 /etc/cadence-relay.env 同源、不同文件（后者是 socat 监听表，4 段，不动）
        │                          └─ relay-vm.sh dnat-apply 读取并落规则
        └─ （仅需钉住域名时）VM /etc/hosts 标记段  <域名> <真实IP>
                                   └─ 容器（重）启动时 podman 以此为基底生成容器 /etc/hosts（F18）
```

四份文件各自的职责，避免混淆：

| 文件 | 段数 | 谁写 | 谁读 | 用途 |
|---|---|---|---|---|
| `/etc/cadence-relay.env`（VM） | 4 | relay.ps1 | relay-vm.sh | socat 监听表（**不动**） |
| `/etc/cadence-relay-dnat.env`（VM） | 5+1 | relay.ps1 | relay-vm.sh | 真实地址 → 桥接地址映射（DNAT） |
| `stack/data/relay-map.env`（安装目录，容器内可见） | 5+1 | relay.ps1 | 容器侧方案（A/B/C） | 同上的容器视角副本（E 主方案下仅作留痕/诊断） |
| VM `/etc/hosts` 标记段 | 2 列 | relay-vm.sh | podman（生成容器 hosts） | 域名 → 真实 IP 钉住（仅在 DNS 不可靠时） |

## 6. 落地步骤

### 6.1 阶段 0：手工验证（今天就能做，零代码改动）

前提（三条都满足才动手）：`relay.ps1 -List` 能看到目标服务（如 `mysql → 10.129.12.75:3306（host 13306 / vm 23306）`）；容器内 `10.89.0.1:23306` 可达；`podman machine ssh 'id -u'` 有输出。

| 步 | 做什么 | 验收 | 回滚 |
|---|---|---|---|
| 0.1 | 记录容器 DNS 现状（只读） | `resolv.conf` 的 nameserver 是网关；`nsswitch` 的 hosts 行含 `files dns` | 无副作用 |
| 0.2 | 判定域名解析结果是否 = 真实 IP | `getent hosts` 输出含 `10.129.12.75` | 无副作用 |
| 0.3 | VM 侧加 DNAT | 容器内 `/dev/tcp` 真实 IP 成功、链计数器增长 | 删链 |
| 0.4 | **域名用例**端到端（含 JVM） | `JVM-OK`；`mysql -h <域名>` 可 `SELECT 1` | 删链 + 撤 hosts 标记段 |
| 0.5 | 反向确认可逆 | 删链后连接重新失败 | 重新加回或进入阶段 1 |

#### 6.1-0.1 容器 DNS 现状（只读）

#### 6.1-0.3 VM 侧加 DNAT（把 IP/端口/网关按实际替换）

```powershell

podman machine ssh 'sudo iptables -w 5 -t nat -C PREROUTING -j CADENCE-DNAT 2>/dev/null || sudo iptables -w 5 -t nat -I PREROUTING 1 -j CADENCE-DNAT'
podman machine ssh 'sudo iptables -w 5 -t nat -A CADENCE-DNAT -d 10.129.12.75/32 -p tcp --dport 3306 -j DNAT --to-destination 10.89.0.1:23306'
podman machine ssh 'sudo iptables -w 5 -t nat -L CADENCE-DNAT -n -v'
```

验收（必须从容器发起；`podman exec` 与容器内其它进程共享同一 netns，等价于"任意进程"）：

```powershell
podman exec devbox bash -c 'timeout 5 bash -c "echo > /dev/tcp/10.129.12.75/3306" && echo CONNECT-OK || echo CONNECT-FAIL'
podman machine ssh 'sudo iptables -w 5 -t nat -L CADENCE-DNAT -n -v; grep 10.129.12.75 /proc/net/nf_conntrack | head -3'
```

判读：

- `CONNECT-OK` 且链 `pkts` 增长 → E-DNAT 成立，进入 0.4；

- `CONNECT-FAIL` 但 `pkts` 增长 → DNAT 生效但目标不可用：先查 socat 与 portproxy（`relay.ps1 -Status`）。

回滚：

```powershell

```

自动生效方式对比：

|---|---|---|---|
| VM 侧独立 systemd unit（+ boot 兜底） | E（主） | 与容器生命周期解耦；VM 重启自恢复；与容器启动**零耦合** | 需要 VM root（relay 已有该通道） |

失败隔离（关键要求：任何代理故障都不得阻断容器启动）：

| 方案 | 机制 |
|---|---|
| E（主） | 规则与容器启动**无耦合**：VM 侧应用失败最多导致"真实地址连不上"，容器照常起 |
| A | ① 应用脚本不用 `set -e` 致命语义，逐条规则失败记日志继续；② `relay.ps1` 侧失败只 `Warn`（与现有"部分服务未通"软失败一致）；③ 若将来改由 entrypoint 调用，必须写成 `if ! step; then log 警告; fi`，**绝不 `exit`** |

### 7.4 域名场景（Q5 已确认存在）

本节回答三件事：容器里谁在解析、解析不对怎么办、DNAT 如何接管。

#### 7.4.1 容器内由谁解析

链路（依据 F16–F18）：

```text
应用 / getaddrinfo
  → /etc/nsswitch.conf  hosts: files dns
      ├─ files：容器 /etc/hosts（podman 生成，以 VM 的 /etc/hosts 为基底）
      └─ dns  ：/etc/resolv.conf 的 nameserver = 网桥网关（例 10.89.0.1）
                 → aardvark-dns（监听网关 :53，F17）
                     ├─ 容器名/别名 → 权威应答
                     └─ 其余（含公司域名）→ 转发上游：
                           VM /etc/resolv.conf → Windows（aTrust 适配器）DNS
```

判定命令（**容器内**执行）：

```bash
cat /etc/resolv.conf
grep '^hosts' /etc/nsswitch.conf
getent hosts <域名>            # 前几条（含 IPv4）
getent ahosts <域名>           # 全部 A/AAAA，用于发现 AAAA 干扰
python3 -c 'import socket,sys; print(socket.getaddrinfo(sys.argv[1], int(sys.argv[2]), proto=socket.IPPROTO_TCP))' <域名> <端口>
```

如何判定"解析结果是否为真实 IP"：

1. 期望值取自 `relay.json`（`relay.ps1 -List` 的"远端地址"列即真实 IP:端口）；
2. `getent hosts <域名> | awk '{print $1}' | sort -u` 的输出与之逐项比对；
3. 一致 → 解析没问题，DNAT 自动接管（§7.4.2）；
4. 不一致或为空 → 走 §7.4.3 / §7.4.4。

补充：`python3` 的 `socket.getaddrinfo` 在 Linux 上与 JVM 走同一条 libc 解析路径，可作为"Java 视角"的代理；若项目显式配置了 `sun.net.spi.nameservice` 自定义解析器，则以项目行为为准（罕见）。

#### 7.4.2 DNAT 只匹配 IP——域名是怎么被接管的

```text
应用 connect("mysql.corp.internal", 3306)
  → getaddrinfo 得到 10.129.12.75                     （解析：§7.4.1）
  → TCP SYN 目的地址 10.129.12.75:3306
  → VM PREROUTING 命中 -d 10.129.12.75/32 --dport 3306 → DNAT → 10.89.0.1:23306
  → 既有 socat → 127.0.0.1:13306 → portproxy → VPN → 真实 MySQL
```

结论：**域名不需要任何额外规则**，只需要保证解析结果是映射表里的真实 IP。只要解析正确，**用域名写与用 IP 写完全等价**；解析不正确时，加再多 DNAT 规则也没用（目的 IP 不匹配）。这也是 §5.3 里第 6 列只做诊断、不参与规则生成的原因。

#### 7.4.3 域名 → 真实 IP 的映射放哪（候选对比）

| 方案 | 落点 | 容器重建后 | 需要改什么 | 生效时机 | 评价 |
|---|---|---|---|---|---|
| **A. VM `/etc/hosts` 标记段（推荐）** | VM | **存活**（每次容器启动 podman 以 VM hosts 为基底重新生成，F18） | 只改 VM（Q1 已允许） | 容器重启后 | 容器/镜像零改动；与 relay 子系统同源；可幂等增删 |
| B. compose `extra_hosts` | 容器 | 存活（声明在 compose） | 改安装目录 `stack/compose.yaml`（`install.ps1` 不覆盖，F14） | 容器重建后 | 声明式、明确；但属容器侧改动，且要用户改自己那份 compose；`podman run` 路线还得写 `--add-host` |
| C. entrypoint 注入 | 镜像/容器 | 存活 | 改镜像 entrypoint（新增第 7 步） | 容器启动 | **不选**：动镜像 + 破坏 6 步契约（F11） |
| D. 容器内手改 `/etc/hosts` | 容器 | **丢失** | 无 | 立即 | 仅用于现场排查；podman 在容器（重）启动时会重写 |
| E. VM 自建 DNS 服务 | VM | 存活 | 安装/配置 resolver，改 redirect | 立即 | **不选**：网关 `:53` 已被 aardvark 占用（F17），容器 resolv.conf 只指向它；截流会连带破坏容器名解析，且 DNS 是 UDP（本方案 DNAT 只做 TCP） |

**推荐 A**，理由：

1. 与 Q1 决策一致（只改 VM 侧），容器与镜像零改动；
2. 容器每次启动都会用 VM `/etc/hosts` 作基底重建自己的 hosts（F18），**不需要在容器内落任何东西**，也不需要 compose 变更；
3. 产物与其他 relay 产物同源（`relay-vm.sh` 在 VM 内幂等维护），`-Teardown` 可对称清理；
4. 只影响被点名的域名，不碰 DNS 链路本身。

**代价（必须写明）**：新增/修改域名后要**重启 devbox 容器**（`podman stop devbox` + `podman start devbox`）才会进入容器 hosts——这是该方法唯一的运维动作。

#### 7.4.4 推荐落地：VM `/etc/hosts` 标记段（命令级）

**只在 §7.4.1 判定"解析不到真实 IP / 解析到错 IP"时才做**；解析正确时不要加，避免无谓的地址固定。

```bash
# 在 VM（podman machine）内以 root 执行
# 1) 看现状（是否已有标记段）
grep -n 'cadence-relay-dnat' /etc/hosts || echo 'no-marker'

# 2) 幂等写入：删旧标记段 → 追加新段（只动自己的行）
python3 - <<'PY'
import pathlib
p = pathlib.Path('/etc/hosts')
begin, end = '# BEGIN cadence-relay-dnat', '# END cadence-relay-dnat'
out, skip = [], False
for line in p.read_text().splitlines():
    s = line.strip()
    if s == begin: skip = True; continue
    if s == end:   skip = False; continue
    if not skip: out.append(line)          # 非自有行原样保留（含空行）
while out and not out[-1].strip(): out.pop()   # 只裁剪尾部空行
out += [begin, '10.129.12.75 mysql.corp.internal   # cadence-relay:mysql', end]
p.write_text('\n'.join(out) + '\n')
PY

# 3) 核对
grep -A3 'BEGIN cadence-relay-dnat' /etc/hosts
```

说明：

- 用 `python3` 而非 `sed -i` 是为了**幂等**且**不动别人的行**（`/etc/hosts` 可能由系统管理）；`relay-vm.sh` 里用 bash + 临时文件实现等价逻辑即可；
- 写入的是**真实 IP**，绝不是桥接地址（指向桥接地址会让应用 `Host`/SNI 与真实主机名不一致，可能触发服务端白名单或证书校验失败，见 §7.4.6）；
- 生效：`podman stop devbox` + `podman start devbox`，然后容器内 `getent hosts mysql.corp.internal` 应返回 `10.129.12.75`；
- 回滚：删除标记段（含两行标记），再重启容器。

#### 7.4.5 排障判据：解析失败 / 解析到错 IP

分层定位，避免把解析问题误判成 DNAT 问题：

| 现象 | 判据（位置） | 结论 |
|---|---|---|
| `getent hosts <域名>` 为空 / `Name or service not known` | 容器内 | 解析失败，继续看下一行 |
| `/etc/resolv.conf` 的 nameserver 不是网关 | 容器内 | 该网络 `dns_enabled=false` 或用了 `--dns`：属另一条解析链路，本方案不覆盖 |
| 容器内失败、VM 内 `getent hosts <域名>` 成功 | VM | aardvark 转发/上游问题：查 `ss -lunp \| grep ':53'`（aardvark 是否在网关监听）与 VM `/etc/resolv.conf` |
| 容器内失败、VM 也失败 | VM / Windows | 上游 DNS 本身解析不了（aTrust DNS 未生效 / 缺 search 域）：Windows 侧 `Resolve-DnsName <域名>` 确认；必要时 §7.4.4 钉住 |
| 解析到**错误 IP**（公网/另一网段） | 容器内 `getent ahosts` | split-horizon：该域名在外部视角是公网地址 → §7.4.4 钉住为真实 IP；**不要**为错 IP 加 DNAT |
| 解析出 AAAA 且连接失败 | `getent ahosts` 有 v6 记录、Java 报 `Network is unreachable` | JDK 可能优先 AAAA（本方案只做 v4）→ 优先 §7.4.4 钉住（hosts 只有 v4 条目时 glibc 只返回 v4）；否则 `JAVA_TOOL_OPTIONS=-Djava.net.preferIPv4Stack=true` 兜底 |
| 解析正确但连接仍失败 | §6.1 0.3 的链计数器 | 问题不在解析：回到 DNAT / socat / portproxy 三段排查 |

取证（镜像无 `dig`/`tcpdump`，用最轻的方式直接问网关 DNS）：

```bash
# 容器内执行：发一个 A 查询给网关，看是否有应答
python3 - <<'PY'
import socket
name = 'mysql.corp.internal'
q = b'\x12\x34\x01\x00\x00\x01\x00\x00\x00\x00\x00\x00'
q += b''.join(bytes([len(p)]) + p.encode() for p in name.split('.')) + b'\x00\x00\x01\x00\x01'
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.settimeout(3)
s.sendto(q, ('10.89.0.1', 53))
try:
    data, _ = s.recvfrom(512)
    print('DNS-REPLY bytes=%d rcode=%d ancount=%d' % (len(data), data[3] & 0xF, (data[6] << 8) | data[7]))
except Exception as e:
    print('DNS-NO-REPLY', e)
PY
```

`rcode=0` 且有应答 → DNS 链路通，问题在"名字本身解析到哪"；`DNS-NO-REPLY` → 网关 53 不通（aardvark 未运行 / 网络未启用 DNS）。

#### 7.4.6 TLS/SNI 与证书

本方案只改报文目的 IP，不改写内容、不终止 TLS：客户端仍以**真实主机名**握手，SNI 与证书校验与直连一致。因此**不要**在 hosts 里把域名指向桥接地址（服务端看到的目标与证书不匹配，或触发基于 Host 的白名单）——这正是 §7.4.4 写"真实 IP"的原因。

### 7.5 VM 侧证据

```powershell
# 规则与计数器
podman machine ssh 'sudo iptables -w 5 -t nat -L CADENCE-DNAT -n -v'
# nft 后端时也可看
podman machine ssh 'sudo nft list ruleset | grep -A6 -i cadence'
# conntrack：应有 <真实IP>:<端口> ↔ <网关>:<vmPort> 的条目
podman machine ssh 'grep 10.129.12.75 /proc/net/nf_conntrack | head -3'
```

**重要**：不要用"VM 里直接 `curl/connect` 真实地址"做自测——那是 OUTPUT 路径，不经过 PREROUTING，会给出假阴性。唯一的权威验证是 §6.1-0.3 的**容器内**探针（域名用例见 §6.1-0.4）。

### 7.6 回归（S4/S5）

mysql -h 127.0.0.1 -P 3306 -u root -p -e 'SELECT 1'

## 8. 风险与边界

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **网段冲突**：某个真实地址恰好落在 `10.89.0.0/16`（网桥网段）或与容器自身地址重叠 | DNAT 目标/回程异常 | 生成端校验：`real_ip` 属于网桥子网时直接报错；落地前 `ip route get <real_ip>` 看是否本就走本地 |
| R2 | **netavark/nftables 多表顺序**（E-DNAT 特有） | DNAT 不生效 | §6.1 门槛实测；不通过切 E-ALIAS（绕开 netfilter） |
| R3 | **网桥网关漂移**（podman 网络重建） | E 的 target 失效；relay 本身也失效 | `-Status` 比对 `target_ip` 与当前 gateway，不符即提示"重跑 setup"（与现有 hop3 提示一致） |
| R4 | **aTrust 重连后桥接地址变化** | 真实地址→vmPort 映射不变（relay.json 静态），但若远端地址本身变了需重建通道 | 用 `relay.ps1` 改址（已有交互流程）；映射表随 setup 重新生成 |
| R5 | **IPv6**：应用优先解析到 AAAA 时绕开本方案 | 连接失败或超时 | 文档标注仅 IPv4；域名场景用 `getent ahosts` 确认实际走向 |
| R6 | **容器重建/升级**：A 方案规则丢失 | 应用重新连不上 | E 无此问题；A 由 `relay.ps1` 重跑补回，README 写明 |
| R7 | **影响面**：E 作用于 `cadence_default` 上所有容器 | 其他容器访问同一真实地址也被重定向 | 这是期望行为；规则只匹配 `-d <real>/32 -p tcp --dport <port>`，不匹配其他流量 |
| R8 | **源 IP 语义**：真实服务看到的源是 Windows 宿主（relay 既有行为） | 若服务端依赖源 IP 白名单，需确认 | 现状已如此（socat→portproxy），本方案不改变；如遇问题反向排查白名单 |
| R9 | **UDP 不支持** | DNS 之外的 UDP 服务不可用 | 明确不在范围；如需扩，要给 relay 增加 UDP 能力（工作量另计） |
| R10 | **VM 重启后规则丢失**（手工阶段） | 恢复原故障 | 阶段 0 只是验证；阶段 1 用 systemd oneshot/boot 兜底保证持久 |
| R11 | **特权面**（A 方案）：`NET_ADMIN` 让容器内任何进程可改自身防火墙 | 安全边界略微收窄 | devbox 本就挂 `docker.sock`（等同宿主 root），边际影响小；仍作为不首选 A 的理由之一 |
| R12 | **`/etc/ld.so.preload` 自锁**（C 方案） | 容器无法 exec | 不采用 C；若将来采用，必须先在旁路容器验证 `.so` |
| R13 | **端口冲突**：E-ALIAS 要在 VM 上监听 `真实IP:真实端口`，若该地址端口已被占用（含误配的重复映射） | 监听起不来，客户端收到本地 RST | 生成端强制 `(real_ip, real_port)` 唯一；应用前 `ss -tlnp \| grep ':<port>'` 预检并显式报占用者；冲突时改用 E-DNAT（不新增监听，无此冲突） |
| R14 | **split-horizon**：公司域名在容器内解析到公网/错误 IP | DNAT 按 IP 匹配，**不会命中**，连接超时 | §6.1 的 0.2 判定；按 §7.4.4 在 VM `/etc/hosts` 钉住为真实 IP；**不要**为错 IP 加 DNAT |
| R15 | **AAAA 优先**：域名有 v6 记录，JDK 先试 v6（本方案只做 v4） | 报 `Network is unreachable`，但同一服务的 IP 用例正常 | §7.4.4 钉住（hosts 只有 v4 条目时 glibc 只返回 v4）；或 `JAVA_TOOL_OPTIONS=-Djava.net.preferIPv4Stack=true` |
| R16 | **VM `/etc/hosts` 可能被系统/云初始化重写** | 钉住的域名失效（回落到 DNS 原行为） | `hosts_apply` 幂等可重入（`-Status` 发现标记段缺失即提示重跑）；标记段带自有前缀便于识别 |
| R17 | **域名条目变更后需重启容器才生效** | 改完立刻测仍旧失败，误判为"方案无效" | 文档与 `-Status` 输出明确提示；`hosts_apply` 后打印"需 `podman stop/start devbox`" |
| R18 | **旧域名残留**：服务改名/删域名后标记段未清理 | 容器里仍把旧名指向旧 IP | `hosts_apply` 每次全量重建标记段（先删后写），天然回收 |
