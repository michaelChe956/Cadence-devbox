# OpenJDK 8 持久切换实施计划

> **执行代理必读：** 逐任务执行本计划，使用 `subagent-driven-development` 或 `executing-plans`；实施前阅读下列设计及规格。每个任务的步骤用复选框追踪，不得越过第一项门槛。

**目标：** 在保持默认 Java 21 的同时，提供容器内 `jdk list` / `jdk use 8|21`，使后续交互与非交互命令使用跨重建持久保存的 JDK。

**架构：** 先隔离实测完整 OpenJDK 8 JDK 的可信来源与运行能力，再新增 external 卷存储额外 JDK 和 `current`。镜像级固定 `JAVA_HOME` / PATH 指向 `current`，命令经校验后原子切换，失败保持旧选择。

**技术栈：** Ubuntu 24.04、Temurin/OpenJDK、Bash、Docker/Podman Compose、PowerShell、pytest。

**规格：** `cadence/designs/2026-09-23_技术方案_OpenJDK8持久切换_v1.0.md`；`openspec/changes/persistent-jdk-selection/{proposal.md,design.md,tasks.md,specs/jdk-selection/spec.md}`。

## 全局约束

- 首次默认镜像内置 Java 21；不弹菜单、不自动识别项目、不做 Skill；只有后续新进程受切换影响。
- 目标是完整 **OpenJDK 8 JDK**，`java` 和 `javac` 均为 8。Temurin 8 是优先待测候选，不是已验证来源。
- 第一任务是硬门槛：目标容器环境中实际下载、校验、隔离安装并执行 `java -version`、`javac -version`。失败时**停止后续任务**、记录证据并请求重新审阅来源；不修改卷、镜像或 PATH。
- 来源及哈希必须独立可信；国内源可配置但不得静默切换不可信代理；尚无已验证的精确 URL/构建号，不能凭猜测写死。若选用已签名 apt 仓库，以签名 Release → Packages → 包 SHA256 的验证链说明来源；另记录下载包实测哈希。
- `devbox/compose.yaml` 的 `services` 保持最后一个顶层键；`devbox/stack/docker-compose.no-sock.yml` 的 `!override` 须同步挂载；Windows 安装器直接 `podman run` 而非使用 compose 启动 devbox，必须同步卷。
- 项目自动提交关闭；计划只标注提交建议，不执行 `git commit`。

### Task 1：验证 OpenJDK 8 安装可行性（OpenSpec 1.1，阻断门槛）

**文件：** 不修改实现。验证记录进入实施时的 `cadence/analysis-docs/`（按当日命名规范）；实验下载存于容器临时目录，不写仓库。

**接口：** 产出经过实测的发行版、具体构建与架构、包 URL/仓库、独立可信校验依据、SHA-256、许可、容器命令与原始输出，供 Task 3 使用；不能以“理论上可安装”替代。

- [ ] 1. 在目标 Ubuntu 24.04、对应 CPU 架构、普通 `dev` 用户和中国大陆网络条件下，确认容器运行能力；记录 `uname -m`、`id`、`cat /etc/os-release`，核对候选完整 OpenJDK 8 JDK 的发行方与仓库/归档来源。
- [ ] 2. 以候选 Temurin 8 为先，核查 USTC Adoptium 源是否为实际目标架构提供 `temurin-8-jdk`；检查签名密钥、签名 Release 及包 SHA-256 链。若该源不提供，调查发行方认可或可独立校验的其他国内可达源；不能将 HTTP 200 记为成功。只记录验证过的精确地址、包版本和上游校验依据。
- [ ] 3. 将发行物下载到隔离临时位置并记录 `sha256sum`；对照独立可信来源校验，隔离安装，执行完整路径下的 `bin/java -version`、`bin/javac -version`；两者须为 8。以非 root 的 `dev` 身份确认可执行，同时检查 JDK 必需的运行时依赖与许可。
- [ ] 4. 记录可复现的具体命令、版本、来源、校验值和原始输出。任一下载、校验、安装、运行步骤失败：记录错误、停止计划后续任务，不伪造可用来源；需要改变发行商或信任策略时先回到设计/契约审阅。

### Task 2：持久状态与统一环境（OpenSpec 2.1、2.2）

**文件：** 修改 `devbox/compose.yaml`、`devbox/stack/docker-compose.no-sock.yml`、`devbox/install.ps1`、`devbox/Dockerfile`、`devbox/entrypoint.sh`；新增小型 `devbox/jdk.sh`（命令与状态单一责任）；修改 `tests/devbox/test_compose_structure.py`、`tests/devbox/test_entrypoint.py`，新增针对状态与切换行为的 `tests/devbox/test_jdk.py`。新增卷名建议 `cadence-jdks`，挂载路径建议 `/home/dev/.cadence/jdks`，固定 `JAVA_HOME=/home/dev/.cadence/jdks/current`；若与首项实测发行包的权限/目录冲突，应先在设计内解释调整。

**接口：** `jdk list`、`jdk use 21`；状态目录含原子替换的 `current`；`jdk use 8` 的下载分支由 Task 3 实现。`entrypoint` 初始化空卷后验证已有状态，不允许损坏状态时悄悄重置。

- [ ] 1. 先添加可观察的失败测试：空状态首次选择 21，已有 8 选择不被覆盖，损坏状态明确报错；Compose 主文件与 no-sock 覆盖文件均保留卷，Windows 直接启动命令显式挂载；新启动的 shell 与非交互命令读取同一 `JAVA_HOME` 和 PATH。运行这些测试，观察预期失败。
- [ ] 2. 在镜像层加入固定 `JAVA_HOME` / PATH、`jdk` 命令入口；新增卷、安装器预创建和直接 `podman run` 挂载、no-sock 覆盖挂载；在初始化阶段仅对空卷选择内置 21，验证已有链接目标的存在和版本。不要把选择逻辑只写入 `.bashrc`。
- [ ] 3. `jdk list` 列出内置和已安装版本并标记 current；`jdk use 21` 以同卷临时链接加原子替换切回内置 JDK。运行定向测试验证默认、恢复、切换和非法状态；用新进程实际检查 `java -version`、`javac -version`、`JAVA_HOME`、`mvn -version` 和 Gradle（可用时）的 JDK，直接容器 exec 不经 shell 启动文件。

### Task 3：按需安装与失败安全（OpenSpec 3.1、3.2）

**文件：** 扩展 `devbox/jdk.sh` 与 `tests/devbox/test_jdk.py`，按 Task 1 证据选择下载配置的放置方式（镜像中只保留经过验证的具体发行版本与可信哈希，不在此预造 URL）。

**接口：** `jdk use 8` 首次安装并切换；既有安装不重复下载；来源可显式配置；不支持主版本和任一失败均保持 `current`。

- [ ] 1. 先写行为测试：完整 JDK 8 包校验及双命令版本检查后才能切换；下载失败、错误哈希、缺少 `javac`、版本不为 8、解包逃逸、中断、无支持版本均非零退出且旧链接/已安装版本不变。使用本地伪造压缩包与独立哈希作故障注入，不用网络作为单元测试依赖；运行并观察失败。
- [ ] 2. 用 Task 1 确认的发行物实现 `jdk use 8`：可信源配置、受限版本/架构、隔离下载与独立哈希校验、安全解包、真实 `java`/`javac` 版本检查、同卷原子发布、最后原子切换；保证错误与中断清理临时数据，旧选择不动。
- [ ] 3. 跑定向测试并用已验证来源在目标容器内真实执行 `jdk use 8`；检查 `jdk list`、`java -version`、`javac -version` 和 Maven/Gradle；重建容器并验证无需重新下载，切回 21 后再重建仍是 21。对错误源及哈希开展失败烟测，确认旧选择不变。

### Task 4：升级说明与端到端收口（OpenSpec 4.1、4.2）

**文件：** 修改 `devbox/README.md`，核对 `devbox/install.ps1`、`devbox/compose.yaml`、`devbox/stack/docker-compose.no-sock.yml` 的安装及升级说明；对应测试按真实行为变化更新。

- [ ] 1. 补充用户步骤：`jdk list`、`jdk use 8`、`jdk use 21`、首次默认与跨重建记忆、已运行进程不变、国内源配置与可信校验失败提示、existing external 卷预建与回滚不删卷；用干净安装和现有安装的升级路径各走一遍。
- [ ] 2. 执行端到端矩阵：空卷 21 → 切 8 → 直接非交互 `java`/`mvn`/`gradle` 与交互命令一致 → 重建沿用 8 → 切回 21 → 重建沿用 21 → 下载失败仍保持 21；单独验证 no-sock 配置与 Windows 安装器的卷挂载。若本机无 Windows/Podman 容器能力，使用可运行环境交付真实执行记录，不把静态测试说成完整端到端。
- [ ] 3. 最后运行相关定向测试与 OpenSpec 严格校验；核对每项验收、清除隔离实验文件、仅汇报文件与证据而不提交。实施与验证通过后再按项目流程请求代码审查。
