# Design: add-transparent-address-mapping

> 详细设计、权衡记录与真机实测证据见 `cadence/designs/2026-10-19_技术方案_容器内地址透明代理_v1.0.md`（v1.3）。本文件只记录架构边界与关键决策。

## Context

既有 relay 通道（`devbox/relay.ps1` + `devbox/relay-vm.sh`）已解决「容器 → VM 中继 → 宿主 portproxy → VPN → 远端」，链路四跳真机跑通。它要求应用把地址换成**桥接地址**（`10.89.0.1:23306`），这对配置中心驱动的工程不可接受。

关键约束（真机实测 2026-10-20，见设计文档 §11.3）：

- **VM 自己到不了真实网段**：`connect(10.129.12.75:3306)` 在 VM 内超时。aTrust 丢弃一切 NAT 转发流量，只有 Windows 宿主发起的连接被放行。⇒ 整网段路由 + MASQUERADE 这条「更省事」的替代路径被排除；VM 到真实地址的唯一通路就是既有 relay 链。
- **目标 VM 无 `iptables`**：podman machine 的 Fedora 44 Container Image 只有 `nft` 与 `ip`。⇒ 规则形态只能是纯 nft；且不安装 `iptables`（会随 podman machine 升级丢失）。
- **容器 netns 与 VM netns 分离**：容器流量必经 VM（默认路由指向网桥网关），因此 VM 侧能改写容器流量的目的地址；反向（VM 自己的流量）不走这条路。
- **relay 服务表是既成的四元组格式**（`name vmport bindaddr hostport`，被 9 处按四元组解析），加列会静默破坏中继目标端口与身份核验 ⇒ 映射信息必须另开文件。

## Goals / Non-Goals

**Goals:**
- 容器内按真实 IP:端口连通远端中间件，应用侧零改动
- 改写目标恒等于中继的实际监听地址（改写后有人接）
- 规则在 VM/宿主重启后自动重建，且不因重启而改变内容
- 用户只跑一个入口、只填一处配置；映射信息是派生物
- 与既有 relay 通道解耦：改写失败不回滚已就绪的通道

**Non-Goals:**
- 不给容器加特权、不改 compose/Dockerfile/entrypoint
- 不改应用工程与配置中心数据
- 不做 UDP 代理、不做 IPv6 目标地址
- 不做域名解析异常的 `/etc/hosts` 钉住（延后项，触发条件见设计文档 §6.2 步骤 2）
- 不做整网段路由/MASQUERADE（真机已排除）

## Decisions

### D1. 改写发生在 VM 的 netfilter，而非容器内

- 为何不在容器内改写：容器 netns 无 `NET_ADMIN`（compose 未声明、镜像无 netfilter 工具），加特权意味着改 compose + 重建镜像 + 存量安装手工迁移；且容器内改写只覆盖该容器，VM 侧改写天然覆盖该网络上所有容器。
- 为何不在宿主（Windows）侧改写：Windows portproxy 只监听 127.0.0.1，容器流量到不了；要在宿主侧做需引入新的转发层。
- 为何不用应用层覆盖（启动参数/环境变量改写数据源 URL）：需逐应用逐键列举，键名要先从配置中心挖出来；且 Spring Cloud Config 客户端的远端配置默认可覆盖本地覆盖，优先级需逐项目实测——本质仍是「改工程配置」的变体，且不满足「透明」。

### D2. 纯 nft，自建表 + 显式 priority

自建 `table ip cadence_dnat`，base chain `prerouting` 用 `type nat hook prerouting priority -101`。同 hook 的 base chain 跨 table 按 priority 升序，`-101` 早于 netavark 的标准 `dstnat`（-100），因此改写**一定先于**容器网络栈的其它改写发生，顺序是确定的而非碰运气。

- 为何不用 `ip nat` 表的 PREROUTING：与现代 podman 的 netavark 规则同为 `dstnat` 优先级而位于不同 table 时，遍历顺序不是强保证——这是本方案唯一的硬门槛，必须靠显式 priority 消除。
- 为何不用 `iptables` 命令：目标 VM 没有该二进制。
- 为何规则先写 `.nft` 文件再 `nft -f`：`nft add chain` 的 `{ type nat hook ... }` 规格含空格与分号，经 Windows→bash 引号层传递会被吃掉引号而语法报错；且 CRLF 行尾被 nft 拒绝。产品化代码运行在 VM 内（不跨 Windows 引号层），但仍统一走「写文件 + `nft -f`」以规避这两类坑。

### D3. 改写目标取 relay 服务表的实际监听地址

目标地址取自既有服务表的 bindaddr/vmPort 两列（该表正是中继进程 `bind=` 的实参），而非现查网桥网关。

- 为何不现查网关：网关漂移时，**真正失效的是 relay 本身**（中继仍绑旧地址、容器也到不了新网关），此时把改写目标改指新网关只会把包送到**无人监听**的地方——比不改更糟。取实际监听地址则保证「改写后有人接」恒成立。
- 为何不写死表里的 target：表里的目标只是生成时的留痕，可能与实际监听漂移；改写目标必须跟着实际监听走。
- 三方比对（映射表目标 / 服务表实际监听 / 当前网关）只做**告警**，不阻断：告警指向「重跑 setup」，规则本身仍按实际监听写，保证可用性优先。
- 判据用「实际监听地址是否仍在本机网卡上」（与既有 relay 状态检查同逻辑、零新依赖）；现查网关仅作诊断增强——VM 内未必有容器编排 CLI，不能让它承载主判定。

### D4. 映射信息另开文件，不扩展既有四元组表

既有服务表被 9 处按四元组解析、3 处仅取前两列，加第 5 列会被折进最后一列而静默破坏中继目标端口与身份核验。映射信息另开文件（5 段必填 + 可选第 6 段域名），两表按**服务名**关联。

- 为何不让消费端自己解析域名：解析结果取决于容器视角，消费端（VM 侧）解析出的是 VM 视角，两者可能不一致（split-horizon）；用 VM 视角反推容器行为是错误的来源。域名由人确认、可审计。

### D5. 单一入口单配置面：域名在同一次问句录入

地址问句从「IP:端口」扩为「IP:端口[ 域名]」，域名是同一行的可选第二段。回车保持地址与域名原值；`-`/`none` 显式清空域名（否则「回车保持原值」会让已录域名永远删不掉）。

- 为何不单独问一次域名：违背用户「不能让用户配这个又配那个」的要求，且多一次交互就多一次遗忘成本。
- 为何域名不参与规则生成：规则按 IP 匹配；域名只用于留痕与诊断。域名解析异常时的 `/etc/hosts` 钉住是**延后项**（触发条件：容器内域名解析不到真实 IP 或解析到错 IP），不与本能力捆绑。

### D6. 规则固化复用既有持久化机制

systemd 可用时新增 oneshot 单元（`RemainAfterExit=yes`、`systemctl enable`）在开机时重放；不可用时**复用**既有的 wsl.conf [boot] 监督循环（每轮幂等重放），MUST NOT 新增第二条 `[boot]` 条目（既有钩子逻辑拒绝外来 `[boot]` 段）。

- 为何单元 ExecStart 必须带 `/bin/bash`：`machine cp` 不保证保留可执行位，仓库自身也从不直接 exec 该脚本（既有调用一律 `sudo bash /usr/local/bin/relay-vm.sh …`）。
- 为何不用 `network-online.target`：WSL 下它没有 wait-online 保证，不能当「就绪」用；就绪性由改写应用的幂等与重试兜底。

### D7. 改写失败不回滚 relay

改写是**附加能力**：中继通道已就绪时，改写失败只告警并由状态查询暴露，不回滚 relay——回滚会连带丢掉已可用的通道（用户的连接地址本就还能用）。失败语义按「部分条目缺失仍继续、全部缺失才失败」分层：部分缺失属配置/生成期错误，重试不自愈，靠日志与状态查询暴露。

## Risks / Trade-offs

- **改写规则在内核态，VM 重启即丢** → 由 systemd oneshot / boot 循环重放重建；单元与映射文件均登记进既有快照/回滚机制，拆除时对称清理（拆除后不得被重放回来）。
- **nft 规则与 netavark 规则的相对顺序** → 显式 `priority -101` 使其确定；真机已验证（`nft list` 显示 `dstnat - 1`）。
- **网桥重建导致监听地址漂移** → 状态查询按「监听地址是否在本机网卡」判定并提示重跑 setup；改写目标仍按实际监听写（规则自洽，通道需重建）。
- **VM 内缺少 netfilter 工具** → 目标 VM 已有 `nft`（Fedora 44 自带）；缺工具时改写失败但不影响 relay 通道。
- **中继被 `--force` 接管时会有 1–5 秒空档** → 属既有 relay 契约；改写规则不感知空档，连接在空档内失败属预期。
- **映射文件与服务表不一致** → 三方比对告警 + 按实际监听写规则；映射文件是派生物，用户不编辑，正常路径不会不一致。
- **nft 规则文件由映射内容生成** → 映射内容在生成端已按 name/IP/端口/域名校验，消费端二次校验（段数、IP、端口、唯一性、域名合法），非法条目直接拒绝而非写入。
- **PowerShell 变量名与内置只读变量冲突**（如 `$Host`）→ 局部变量/形参一律避开内置只读名；此坑在 WinPS 5.1 上会直接失败，行为级用例需在有 pwsh 的环境实跑（本机装 pwsh 7.4.6 后暴露 18 个失败，已全部修复）。

## Migration Plan

存量配置零迁移：配置文件无域名信息即视为未录入，既有服务全部沿用原值。既有 relay 通道行为不变（改写是附加能力）。

回滚策略：`relay.ps1 -Teardown` 对称拆除（规则、VM 侧单元、映射文件）；只想手工清规则时删除 VM 侧自有表即可（幂等，不影响其它表）。
